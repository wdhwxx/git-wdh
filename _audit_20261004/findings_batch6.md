- **整改建议**：在 `config/live_config.yaml` 增设备案字段（报备编号、报备日期、账户标识、策略标识、软件版本、备案状态）并在 `myquant/live/acceptance.py` 的准入判定中增加合规项，使 `--mode live --confirm-live` 启动前校验备案状态，未备案即拒绝启动；在 `myquant/live/engine.py` 启动自检处输出备案信息快照并落盘；新增异常交易监控模块（撤单率、报单频次、自成交、频繁撤单占比）作为实盘必装组件，命中即暂停并生成报告。上述备案字段与条款映射**需持牌律师/合规官确认**，条款以证监会/交易所官网最新原文为准。

### KP-P6-02 日志仅保留 7 天，清理工具可绕过 dry-run 直接删除审计证据

- **事实**：`cleanup_service.py:695` 定义 `LOG_KEEP_DAYS: int = 7`，`:712` 以 `cutoff = datetime.now() - timedelta(days=LOG_KEEP_DAYS)` 计算过期点，`:728` 将更早的日志文件加入待删列表（K 类）。`logger.py:228-262` 三个 `RotatingFileHandler` 仅按 `maxBytes`/`backupCount` 轮转，无时限型保留策略。执行层 `execute_plan`（`:895-926`）直接对 `plan.delete_candidates()` 逐个 `path.unlink()`（`:911`）或 `shutil.rmtree(path)`（`:915`），函数体内**不校验 `plan.options.execute`**。调用点三处：`scripts/垃圾数据清理.py:106` 显式以 `if args.execute and plan.junk.items:` 守卫，`scripts/清理历史回测输出.py:113` 同样受入口开关约束，但 `myquant/gui/cleanup_dialog.py:440` 在确认流程后直接调用 `execute_plan(plan)`。全库检索 `LOG_KEEP_DAYS` 仅命中清理服务自身，无配置项、无审批点、无归档前置动作。
- **推断**：dry-run 语义只在 CLI 入口成立，在服务层不成立——任何持有 `CleanupPlan` 的调用方（含 GUI 及未来新增调用方）都能删除文件；日志这类承载交易留痕与风控事件的证据，与 `__pycache__`、测试残留同处一个删除通道，无差别保护。7 天留存窗口短于「仿真运行 ≥1 个月」（`acceptance.py:45` 的 `run_days_min = 30`）的取证需求，也短于多数月度复核与监管追溯周期，故准入评估、绩效归因、风控事件复盘在事后很可能无原始日志可查。

- **风险影响**：交易与风控证据在 7 天后被例行清理，异常事件、强平决策、拒单原因无法复原；审计与监管问询时无法提供原始记录；争议情形下举证不利；若清理被误操作，`outputs/`、`processed/` 下的整目录删除会扩大数据损失面。

### KP-P6-03 强平「假成功」污染审计轨迹：dry-run 回传 executed=True 且上层丢弃返回值不再升级

- **维度**：内控与审计轨迹 / 风控事件留痕
- **位置**：`myquant/live/emergency_liquidation.py:130-132`、`:247-249`、`:287`；`myquant/live/engine.py:1775-1806`、`:1886-1895`；`myquant/risk/guardian.py:494-514`
- **证据等级**：A（四段代码的判定条件、返回值与调用方行为均为直读原文）
- **优先级 / 风险等级**：P1 高（结论级留痕失真：记录显示「已执行」，实际未下一单）
- **事实**：`EmergencyLiquidationService.execute` 以 `confirm=False` 调用时走预览分支：`_liquidate_positions` 在未确认时执行 `success += 1  # dry_run 计划项计入 success（预览语义）`（`:287`），状态记为 `status = "PLANNED"`、`reason = "预览：未真实下单（加 --confirm 执行）"`（`:247-249`）；随后汇总 `report["ok"] = report["liquidation"]["failed"] == 0 and not report["errors"]`（`:130`），故 dry-run 亦得 `ok=True`。引擎侧 `engine.py:1797-1806` 以 `confirm=False` 调用服务后取 `ok = bool(report.get("ok"))` 并 `return ok`，同时打印 `logger.critical(... mode={report.get('mode','?')} ok={ok})`。守护侧 `guardian.py:500-508` 将该返回值直接写入决策：`executed = self._force_close_callback("all", None)` → `decision.executed = executed`，并在 `executed` 为真时记录「强制平仓所有已执行」。而 `engine.py:1891-1892` 调用 `self._guardian.force_close_all(...)` 时**丢弃返回值**，既不重试也不升级为人工强平。
- **推断**：守护决策记录与引擎 CRITICAL 日志共同构成对强平事件的唯一留痕，而二者均把「生成计划」表述为「已执行」；审计者若只读日志与决策记录，会得出「风险已被处置」的结论，而实际持仓仍在场。上层 `_guardian_patrol` 丢弃返回值后，即使 dry-run 返回真假值也没有驱动人工 SOP 的路径，人工兜底仅有代码注释而无触发机制。日志字段区分 `mode` 与 `ok` 但未区分「已执行/已计划」，日志消费方（含未来监管报送）无法据此还原真相。
- **未知**：`paper/sim` 模式下真实平仓是否另有 `--confirm` 人工链路（`scripts/一键平仓.py --confirm` 存在，但是否纳入运维 SOP 未取证）；是否有外部监控读取 `report["mode"]` 做区分；一次真实窗口内强平触发的历史次数与处置结果。
- **风险影响**：熔断强平未落地而系统宣告已执行，风险敞口持续暴露；事后复盘与责任认定失去可信依据；若该留痕被用于对外报送，属实质性不实陈述。
- **可能性**：已有事件（dry-run 返回 `ok=True` 是当前代码的确定性行为，每一次强平触发均产生一条失真的 CRITICAL 留痕）。
- **根因**：技术 —— 预览语义与执行语义共用同一 `ok` 字段，调用方未按 `mode` 分支解释结果。
- **整改建议**：① `myquant/live/emergency_liquidation.py`：将 `report["ok"]` 语义拆分为 `report["ok"]`（链路未出错）与 `report["executed"]`（是否真实下单，dry-run 恒为 `False`）；`_liquidate_positions` 在 dry-run 下不计入 `success` 而计入 `planned`。② `myquant/live/engine.py:_on_force_close` 返回 `bool(report.get("executed"))`，并在日志中显式打印 `executed=` 与 `mode=`。③ `myquant/live/engine.py:_guardian_patrol` 接收返回值，若为 `False` 则立即发出 CRITICAL 告警并要求人工确认（接入现有告警通道），`myquant/risk/guardian.py` 的 `decision.executed` 相应改由 `executed` 字段驱动。
- **验证方法（DoD）**：① 单元测试：以 `confirm=False` 调用服务，断言 `report["executed"] is False` 且 `report["planned"] > 0`；② 单元测试：桩件使回调返回 `False`，断言 `_guardian_patrol` 触发告警且 `decision.executed is False`；③ 检索确认全库无「dry-run 计 success」写法；④ 日志样例中 `executed=False` 与 `mode=DRY_RUN` 成对出现。
- **最坏情形**：真实熔断场景下强平触发后系统记录「已执行」、无告警升级、无人介入，持仓在下跌中全程暴露，事后审计依据指向一份虚假的成功记录。
- **是否需法律顾问确认**：否
- **管理层回复**：待管理层回复
