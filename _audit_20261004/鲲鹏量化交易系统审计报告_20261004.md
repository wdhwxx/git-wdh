#### 发现 KP-P3-01 T+1 冻结只增不减，买入次日仍不可卖出

- **维度**：交易执行 / 交易规则一致性
- **位置**：`myquant/live/brokers/paper_broker.py:158,285-286,808-809,825-834`；`myquant/live/brokers/qmt_broker.py:1384`
- **证据等级**：A（代码原文逐字核对，且全项目检索 `settle_t1` 调用点可复核）
- **事实**：买入成交时累加冻结 `self._t1_holdings[symbol] = self._t1_holdings.get(symbol, 0) + trade.quantity`（`:809`）；下单前置检查用 `available_qty = pos.quantity - t1_frozen`（`:286`），不足即拒单（`:288-298`）。释放仅靠 `settle_t1()` 内的 `self._t1_holdings.clear()`（`:831-832`）。**该函数自身的 docstring 明确写明「实盘时由 scheduler 在每日收盘后调用」（`paper_broker.py:827-829`）**，但全项目检索 `settle_t1` 仅命中 `scripts/双券商模拟实盘.py:308,350`、`scripts/实盘模拟回测.py:275` 两处演示脚本；`myquant/live/engine.py`、`myquant/live/scheduler.py` **无任何调用点**，`attach_engine` 只注册巡检、日报、补单三类任务。QMT 适配器侧的 `settle_t1`（`qmt_broker.py:1384-1392`）docstring 注明「真实 QMT 由券商结算，本方法仅 SIM 模式模拟日终结算」——即 **SIM 模式同样依赖此调用，而该调用同样缺失**。
- **推断**：实盘与仿真多日连续运行时冻结量只增不减，次日卖单被本地前置检查永久拒绝，止损、止盈与强平出口被自锁。
- **未知**：是否存在运行时动态注入（`getattr` 或任务表）；QMT 实盘端是否由券商 T+1 校验绕过本地冻结。
- **风险影响**：持仓无法退出，风险敞口长时间裸露；仿真期无法验证可平仓行为，仿真→实盘准入证据链失效。
- **可能性**：控制完全缺失
- **根因**：技术 —— 日切结算函数已实现但未接入任何生产调度生命周期。
- **整改建议**：在 `myquant/live/scheduler.py` 的收盘任务中注册日切任务，调用 broker_manager 各通道 `settle_t1()`；引擎启动时对存量持仓做一次解冻初始化。
- **验证方法（DoD）**：单测「T 日买入→日切→可卖数量恢复→卖单通过」；集成测试连跑两个交易日，断言无「可卖数量不足」拒单日志。
- **最坏情形**：实盘遇急跌无法卖出，强平流程亦被拒，损失无上限扩大。
- **是否需法律顾问确认**：否

#### 发现 KP-P2-10 生产撮合引擎的涨跌停不可成交约束恒为空转：`Bar.pre_close` 恒为 0

- **维度**：回测与仿真 / 实盘一致性
- **位置**：`myquant/backtest/mixed_engine.py:948`；`myquant/backtest/order_matcher.py:370,383-386`；`scripts/数据导出_DB到processed.py:109`；`myquant/data_access/provider.py:67,566-567`；`myquant/backtest/vectorized_engine.py:455-459`；`myquant/backtest/engine.py:694-702`
- **证据等级**：A（构造 Bar、撮合校验、导出 SQL 三处原文逐字核对）
- **事实**：生产主力引擎构造 Bar 时 `pre_close=float(row.get("前收盘价", 0))`（`mixed_engine.py:948`）。processed 数据的唯一导出 SQL 为 `SELECT trade_date, open, high, low, close, volume, amount, pct_chg, amplitude, volume_ratio, turnover, float_share, pe_dynamic`（导出脚本第 109 行），**不含前收盘价**；全项目检索 `前收盘价` 仅命中映射表、docstring 与注释，**无任何写入点**，故 `row.get("前收盘价", 0)` 恒取 0。撮合层校验为 `if self.enable_price_limit and bar.pre_close > 0:`（`order_matcher.py:384`），因此恒为假，其自身注释亦承认「pre_close<=0 时跳过涨跌停检查（数据不足）」（`:370`）。对照之下 vectorized 引擎自带兜底 `else: pre_closes = np.concatenate([[np.nan], closes[:-1]])`（`:456-459`），event 引擎则根本不传 `pre_close`（`engine.py:694-702`）。
- **推断**：mixed（生产主力）与 event（自称真值基准）两引擎在回测中**不会拦截「涨停开盘买入、跌停开盘卖出」**；只有 vectorized 引擎因前收兜底而近似正确。三引擎的一致性对拍会把这一「可交易性约束是否生效」的口径差当作可接受的数值误差。
- **未知**：processed 目录下历史 parquet 是否在早期版本曾含该列（本次无 python 可执行，未列文件列名）；样本期内涨停开盘样本占比，故未量化对历史绩效的具体影响幅度。
- **风险影响**：回测净值与实盘可执行性出现结构性高估，收益与容量结论不可用于真钱决策；该偏差方向单向乐观，不会自然抵消。
- **可能性**：控制完全缺失（校验条件在生产路径上恒为假，且缺失时静默跳过而非阻断）
- **根因**：技术 —— 撮合层的可交易性校验依赖一个导出管道并不存在的列，缺失时默认值 0 使校验静默失效，且三引擎各自构造 Bar 未统一。
- **整改建议**：①导出 SQL 补 `pre_close` 并重导 processed；②在 `myquant/backtest/data_loader.py` 加载层统一派生 `前收盘价 = close.shift(1)` 作为兜底并写回 DataFrame；③`order_matcher.py:384` 与 event 引擎在 `pre_close<=0` 时改为抛错或记 warning 并在 `result.extra` 标记 `price_limit_checked=False`，禁止静默跳过；④CI 增加「processed 列集合必须包含前收盘价」的契约断言。
- **验证方法（DoD）**：构造含涨停开盘日的样本，断言 mixed/vectorized/event 三引擎在该日买单成交数为 0 且撮合日志出现涨跌停拦截记录；重跑同一区间并对比修正前后净值差异，差异纳入报告披露。
- **最坏情形**：对外披露的绩效包含大量实际不可成交的涨停买入，按该绩效放大资金实盘后无法复现。
- **是否需法律顾问确认**：否

#### 发现 KP-P2-11 第二道防未来防线的失败结果会被 `mark_complete` 覆盖为「已完成」

- **维度**：回测与仿真 / 防未来函数

#### 发现 KP-P4-02 无订单/成交/持仓关系账，仅份数受限的 JSON 快照与轮转日志

- **维度**：对账 / 审计追踪
- **位置**：`myquant/database/schema.py:32-43,52-285`；`myquant/live/state_store.py:503-528,576-616`；`myquant/core/logger.py:228-262`
- **证据等级**：A（建表 SQL 与表名常量原文可读）
- **事实**：`TABLE_NAMES` 仅 10 张表（行情/财务/因子/复权/股本/策略状态/数据源/同步/清洗元信息/脏数据），全部建表 SQL 中**无 order/trade/position 表**，`strategy_state` 仅通用键值 JSON；实盘持久化落在 JSON 快照（含账户/持仓/订单与 sha256 校验），`delete_old` 默认仅保留 50 份且不落逐笔成交；日志为 `RotatingFileHandler`，按 `maxBytes`/`backupCount` 轮转覆盖。
- **推断**：缺少可长期查询的委托—成交—持仓关系流水，审计追踪依赖可被清理的快照与日志。

- **验证方法（DoD）**：成交后可在 DB 查到与 broker 一致的逐笔记录；快照删除不影响历史查询。
- **最坏情形**：核查无法举证，交易责任与损失无法界定。
- **是否需法律顾问确认**：是（涉及交易资料保存义务）

#### 发现 KP-P4-03 实盘 LIVE 模式本地账本不记费用，现金口径系统性偏离

- **维度**：组合与资金 / 账务真实性
- **位置**：`myquant/live/brokers/qmt_broker.py:1192-1205`（工作底稿全文见 `findings_batch4.md`）
- **证据等级**：A
- **事实与影响**：本地账本在 LIVE 模式的成交处理中未按 `fee_common` 口径计提佣金、印花税与过户费，导致本地现金始终高于券商实际可用资金，差额随交易笔数累积。
- **推断**：以本地现金为准的资金检查会持续偏乐观，最终在实盘出现「本地可用但券商不足」的拒单或被动缩量。
- **整改建议**：在成交回调内统一调用费用计算入口计提并从现金扣除；与券商资金查询做日终核对。
- **验证方法（DoD）**：单测断言本地现金 = 初始资金 − 成交金额 − 累计费用；对照券商日终资金差额在容差内。
- **最坏情形**：资金检查失效导致超买被拒，策略执行与预期仓位系统性偏离。
- **是否需法律顾问确认**：否

#### 发现 KP-P6-01 程序化交易报备、高频与异常交易控制点全缺失

- **维度**：合规与治理 / 程序化交易报备
- **位置**：`docs/仿真模拟盘运行制度.md:109,119-120,132,144`；`myquant/live/acceptance.py:30`；`config/live_config.yaml`（全文）
- **证据等级**：B（全库检索与调用点枚举为确定性事实：`程序化交易|报备|高频交易|异常交易|报送` 在 `myquant/` 下零命中，在 `docs/` 下仅命中 12 处纯文字表述，无任何模块、开关、字段或校验函数与之对应）
- **事实**：制度文档把「程序化报备」列为实盘前必须向券商确认的外部依赖项，并写明「程序化交易按监管要求报备」与「个人程序化须在券商封闭终端内进行」；但代码侧形态全无：`_ACCEPTABLE_MODES = frozenset({"paper", "sim"})` 仅约束运行模式，`config/live_config.yaml` 全文无报备状态、账户标识、策略标识、高频判定或异常交易监控任何配置键。
- **推断**：报备义务被完整外包给「联系券商客户经理」这一人工动作；系统既不记录报备状态，也不阻止未报备配置进入实盘链路，即「未报备即实盘」在技术上是可达状态；高频与异常交易的识别、监控、留痕、报告控制点不存在，属控制完全缺失。
- **未知**：账户是否已在券商或交易所实际完成报备（需回执/报备编号）；监管对高频交易的量化认定口径与本系统实际下单频率的对照结论；账户主体（个人/机构）差异；是否存在线下台账。
- **风险影响**：未报备或报备信息与实际账户、策略、软件不一致时可能触发监管处置、限制交易权限；异常交易无从留痕，被问询时无法自证。
- **可能性**：控制完全缺失
- **根因**：合规 —— 监管义务只落在制度文本与人工沟通层，未转化为系统内的状态、门禁与留痕。
- **整改建议**：在 `config/live_config.yaml` 增设备案字段（报备编号、报备日期、账户标识、策略标识、软件版本、备案状态），并在 `myquant/live/acceptance.py` 的准入判定中增加合规项，使 `--mode live --confirm-live` 启动前校验备案状态，未备案即拒绝启动；启动自检输出备案快照并落盘；新增异常交易监控模块（撤单率、报单频次、自成交、频繁撤单占比）作为实盘必装组件，命中即暂停并生成报告。**上述备案字段与条款映射需持牌律师/合规官确认，条款以证监会/交易所官网最新原文为准。**
- **验证方法（DoD）**：① 配置含备案字段且准入器存在合规判定分支；② 构造备案缺失配置执行实盘启动，进程以非零码退出并打印缺失项；③ 异常交易模块有超阈值撤单率触发暂停的单测；④ 由持牌律师/合规官书面确认字段与条款映射并归档。
- **最坏情形**：以未报备状态长期实盘运行，被问询时既无报备凭证也无异常交易留痕，账户被限制交易，在途持仓无法按计划退出。
- **是否需法律顾问确认**：**是**

**矩阵校验**：按**净发现**口径，10（高×严重，即全部 P0）＋ 25（高×高）＋ 9（高×中）＋ 2（中×高）＋ 2（中×中）＋ 1（低×低）＝ **49**；第 50 项为 KP-M05 复合发现本身（其构成项 KP-P5-10、KP-P6-02 已分别在「高×高」格计入原始行），故总数 **50**，与 §0.2 一致。上表「高×高」格按 31 个**行项**列出（含 KP-M01 ~ KP-M05 及其构成项），净计数为 25 项；差异全部来自合并（KP-M03 含 2 行、KP-M04 含 2 行、KP-M02 含 2 行、KP-M01 含 2 行，共减 6 项，另加各自的复合项，净差 6）。§0.2 为最终口径。

**矩阵读数（三项结论）**：

1. **矩阵左上区域几乎为空，右下区域高度拥挤。** 这说明缺陷不是零散的「实现难点」，而是集中在「控制完全缺失且后果严重」与「控制存在但未生效」两类，两种情形都落在可被工程手段关闭的区间，前提是先改变判定标准（见 R1）。
2. **10 项 P0 全部位于「高可能性 × 严重影响」格。** 这是本次给出 No-Go 建议的直接依据：不是单一高危缺陷，而是「同类缺陷在同一系统内反复出现」的模式。
3. **无一项落在「低 × 低」格。** 本次审计未发现可以忽略的观察项；唯一的 P3（KP-P6-06）为文档一致性问题，仍因涉及「整改真实性不可复核」而被登记为低风险而非信息级。

## 8. 审计结论

### 8.1 总体成熟度评分

采用提示词第八章的 0–5 行为锚定评分（0＝无制度；1＝有制度无执行证据；2＝局部执行；3＝有执行证据但无度量与复盘；4＝有度量、复盘与闭环；5＝持续度量、自动化验证、外部复核）。

**总体成熟度：1.8 / 5 —— 介于「有制度、无执行证据」与「局部执行」之间。**

评分理由（行为锚定，非印象）：

- **能得 1 分以上的依据**：制度与实现确实存在——11 条实盘风控规则、三引擎回测架构、Alembic 迁移、CI 七作业流水线、清理与备份工具、模型注册与 HMAC 签名、数据质量探查与指标体系、较完整的文档体系。部分控制确实在执行（例如回测的费用模型、数据清洗流水线、结构化的 GUI 与入口分层）。
- **不能超过 2 分的依据**：本次审计在每一个关键控制类别上都找到「实现存在但控制不生效」的证据（§4.5 根因簇 R1），且**未取得任何测试执行报告、运行日志或度量记录**——即「有执行证据」这一锚定条件本身不成立。凡「已验证/已闭环」的主张均来自被审计方自述，且已发现自述之间互相矛盾（KP-P6-06）与自述与代码矛盾（KP-P6-04）。
- **不能达到 3 分及以上的依据**：3 分要求「有执行证据但无度量与复盘」。当前状态是执行证据本身缺失（无测试报告、无运行台账、无告警记录），故不满足。
