## 1. 背景与目标

### 1.1 问题定义

- **未来函数（look-ahead bias）**：指标/信号在计算时使用了决策时点之后的数据。典型形态——同根 K 线用收盘价下单、`rolling(center=True)`、`.shift(-n)`、全序列标准化后再切片、用未来复权/财务信息修正历史价。
- **数据泄漏（data leakage）**：更宽泛，含训练/验证集污染、标签泄漏、横截面泄漏（用未来全体股票统计）、幸存者偏差等。
- **v2.3 新增第三类：休眠缺陷（dormant defect）**：数据层已产出穿越值，但当前无任何消费方引用该列。它**尚未污染任何结论**，但一旦有策略/特征引用即转为活动泄漏。**此类缺陷的正确处置是"堵在消费入口"，而非"按已污染结论的高优先级紧急重导出"**——这是 v2.2 影响面判断偏重的根源。

### 1.2 关键阶段判断

> 骨架已建好，基础策略已落地，完整策略后期开发。

含义：
1. **当前是建门禁的最佳窗口期**——策略代码未大规模铺开，契约可以先定。
2. 门禁应**前置到骨架层**，而不是事后补。
3. 策略开发**按契约进行**，门禁在入口拦截，不做事后扫存量。
4. 多策略类型压力尚小，但契约必须提前定，否则后期返工。

> **v2.2 补充**：以上对**策略侧**成立。但**数据层已存在既存穿越缺陷**（§6.4.1），不适用"不做事后扫存量"——数据层必须先收口，否则门禁会为穿越数据背书。
>
> **v2.3 校准**：数据层收口仍然必要，但其**性质是"拆弹"而非"救灾"**。经实测该穿越列无消费方（§12.3-1），故：① 不存在被污染的历史回测/训练结论需要隔离；② 不需要为修正历史结论而全量重导出；③ 收口工作的重心应放在"**防止未来被消费**"（消费侧门禁）与"**防止修复被静默吞掉**"（fail-open 治理），而非数据重导。

### 1.3 门禁目标

把"防泄漏"从零散代码埋点升级为**强制、可审计、可豁免**的工程门禁体系：

1. **台账层**：每个数据列的时点日基显式登记、可机读（§6.1）；
2. **契约层**：每个策略/因子/特征/标签声明 `decision_time` 与 `available_time`；
3. **消费层（v2.3 新增）**：任何策略/特征引用数据列时，校验该列在台账中的 `severity`，引用阻断档即报红（§6.1.3 / R11 / RL-13）；
4. **写代码阶段**：静态 AST 扫描拦截泄漏模式；
5. **运行时**：现有 guard 补强 + 截断重算 + **fail-open 可观测化**；
6. **统计层**：shuffle-label + 特征-标签对齐 + 训练产物时间校验；
7. **数据层**：PIT as-of 校验 + 列级 `available_time`；
8. **治理层**：红线台账 + 豁免流 + 审计报告 + CI 矩阵。

### 2.3 复权链路（v2.3 补全，已核验）

v2.2 只描述了"导出 SQL 写死 `adjust='raw'`"，未查回测**实际消费**的复权值，易被读作"回测跑 raw"。完整链路如下：

| 环节 | 位置 | 事实 |
|---|---|---|
| 导出层 | `scripts/数据导出_DB到processed.py:111` | `WHERE … adjust='raw'`，parquet **只存 raw** |
| 消费期现算 | `myquant/data_access/provider.py:471-476` | `processed` 只存 raw，`hfq/qfq` 按因子表**内存变换** |
| 实际配置 | `config/backtest_config.yaml:3274`、`config/backtest_kunpeng.yaml:3250` | **`adjust: hfq`**（两份真实配置均为后复权） |
| 示例配置 | `config/backtest_config.example.yaml:115` | `adjust: "raw"`，注释标 `qfq（预留）` |
| 注入点 | `run_回测入口.py:295-299` | `HistoricalDataProvider(default_adjust=data_cfg.get("adjust", "raw"))` |

**结论**：回测实际跑的是 **hfq（后复权）现算**，不是 raw。这一点必须写进台账与契约，否则"复权语义未锚定"的风险描述会指向错误的落点。

## 4. 缺口诊断（七层门禁模型：L-1 契约层 + L0–L4，含 v2.3 新增 L0.5 消费层）

| 层 | 现状 | 缺口（本方案补） |
|---|---|---|
| **L-1 契约层** | 无 | 无 `decision_time` 契约；策略注册表未带契约元数据；无 `available_time` 声明；**契约主键未定死** |
| **L0 数据层** | `ann_date` PIT（单路）、复权因子 PIT（实现正确）、data_versioner | ① `每股收益` 时点穿越（导出层 + 增量层）；② `processed` parquet 无列级 `available_time` 派生；③ 同一语义四套日基未收敛；④ **复权 `end_date` 传参纪律与 `adjust_strict` 默认值未治理**（v2.3 改写，非"语义未锚定"） |
| **L0.5 消费层（v2.3 新增）** | **完全缺失** | **无任何门禁校验"哪些列被谁引用"**。台账即使登记了 `severity: 阻断`，也没有执行点消费这个标记——休眠穿越列被引用的瞬间无人报警 |
| **L1 特征/因子层** | 数据指纹、IC/ICIR+经济逻辑、ML 特征截断重算 | ① 无静态 AST 扫描；② 横截面 as-of 对齐无专门检测；③ 因子因果无统一契约 |
| **L2 模型层** | time_series_split、walk-forward、`train_end_time`+推理守卫 | ① 无 shuffle-label sanity test；② **训练侧**写入时间校验缺失（推理侧已有）；③ 参数优化/MC 种子未统一治理（种子已基本存在，仅缺 sidecar） |
| **L3 执行层** | 四铁律 + 轻量 guard | ① 策略自定义**内嵌计算**不被引擎 guard 覆盖；② **现有 guard 自身多为空转/恒真**（§3）；③ **三处 fail-open 使防线可被静默绕过**（v2.3 新增） |
| **L4 治理层** | CI 强制 + audit_log 哈希链 + 架构门禁 | ① 无统一红线台账/豁免审批流（且**无豁免流实现落点**）；② 无泄漏审计报告产物；③ live_config 真实文件未纳入 guard 断言 |

### 4.1 缺口优先级（v2.3 修订）

| 优先级 | 缺口 | 影响 | 阶段 |

### 5.3 数据层设计（L0）——列级台账驱动

- **前置**：先出**列级时点台账**（`config/data_time_semantics.yaml` + 文档），逐列登记派生来源、日基、现状判定与目标日基（见 §6.1）。
- **回测主路径**：`scripts/数据导出_DB到processed.py` 导出时**按列派生 `available_time`**——日线行情列取 `trade_date`；**财务类列取 `eff_disclosure_date + 1`**（不得一律用 `trade_date`）。并写导出批次 sidecar。
- **SQLite**：仅在确需区分"修订版本"的表（财务修正、复权事件）按需加 `available_time`/复用事件时间戳，避免全 A 日线大表迁移。
- **复权语义（v2.3 改写）**：复权实现**已 PIT 正确**（§3 表格倒数第 4 行），不需新建规则。真正要治理的是两点：
  1. **`end_date` 传参纪律**：`get_bars`/`load_data` 的 `end_date` 默认值为 `None`（`provider.py:131`、`:352`），此时 `_get_factor_lookup(as_of=None)` 会取**全量**因子表。须在契约层强制"回测/实盘调用必须传 `end_date`"，并对 `None` 路径加断言或告警。
  2. **`adjust_strict` 默认值治理**：`_apply_factor_adjust(adjust_strict=False)`（`:535`）时，无因子事件**静默降级为 raw 并仅告警**（`:545-552`）。降级后价格口径与同批次其他标的不一致，**回测结果不可比却无阻断**。建议：真实回测配置中 `adjust_strict: true`，或至少在 sidecar 记录降级标的清单。
- **PIT 访问**：扩展 `data_access/provider.py` 的 `HistoricalDataProvider`，增加 `load_asof(decision_time)` 变体与 `asof_join`。
- **版本联动**：时点日基变更须同步 `utils/data_versioner.py` 的 rev 机制，使"禁止跨口径比较历史结论"生效。
  > **v2.3 校准**：因 §12.3-1 已确认穿越列无消费方、不存在需隔离的历史结论，本项**从"必须"降为"应做"**——它是防止未来同类变更出问题的机制，而非修正既有污染的手段。

def assert_all_gates_pass(strategy_id, decision_time):
    contract.validate(strategy_id, decision_time)        # 1. 契约
    static_scan.scan(strategy_id)                         # 2. 静态扫描（结果按内容哈希缓存）

## 6. 分阶段施工方案（v2.3 修订）

### 6.0 四条修订原则

v2.1 的阶段划分建立在两个前提上：「存量 guard 是可用资产」与「数据层无存量泄漏」。v2.2 复核结论是**两个前提都不成立**。v2.3 在此基础上补充第三、四条：

1. **契约与台账分离**：策略契约（声明式元数据）可以先行；但**数据可用性必须由列级时点台账驱动**，不能由契约里手写的 `available_time` 字符串驱动。
2. **门禁先证明自己能拦**：每道门禁必须自带"注入泄漏必报红"的反向测试（项目已有 `test_p211_terminal_state.py:86-87`、`test_p2_anti_future_config.py` 这类门禁元测试传统——前者要触发违规，必须手工把 `_bar_timestamps` 改成 `[ts[-1], ts[0]] + ts[1:-1]`，这恰好反证了 §6.3-1）。**无反向测试的门禁不计入验收**。
3. **存量 guard 按实测效力重新登记**：登记口径从"文件存在"改为"运行期是否真的能拦截"，分三档如实标注（§3）。
4. **（v2.3 新增）影响面必须由消费侧实证，不得由供给侧推定**：一个穿越列的真实危害 = 日基错误 × 消费方数量。判定"已污染"前必须实测消费面；**"数据写错了"不等于"结论被污染了"**。同理，防泄漏门禁必须有一层管住"谁在引用"，否则台账的 `severity` 标记没有任何执行点，是纯文档。

### 6.1 阶段 0-P：列级时点台账（可与 0-A 并行，约 0.5 周）

**为什么必须先做**：`datasets/processed/*.parquet` 的同一组业务列，其**派生来源与时点日基各不相同**（见 §6.4.2）。若先按 v2.1 §5.3 派生 `available_time` 列，会给当前仍穿越的「每股收益」打上 `available_time ≡ trade_date` 标签——**把一份穿越数据包装成已声明 PIT 的数据，比现状更危险**，门禁此后将为它背书。故 `available_time` 派生必须晚于本阶段。

> **v2.3 补充的第二个理由**：本阶段产出的 `severity` 档位是 **L0.5 消费侧门禁的唯一数据源**。台账不做，R11/RL-13 无从判定。因此台账可与 0-A 并行开工，但**必须早于消费侧门禁的验收**。

**新增**：

1. `docs/未来函数与数据泄漏门禁/数据列时点台账.md`
   - 覆盖 `datasets/processed` 全部 13 个业务列 + 导出层/增量层**派生列**；
   - 每列登记：派生来源文件、日基（date basis）、现状判定（通过/穿越/保守）、目标日基、档位、**当前消费方清单（v2.3 新增）**。

#### 6.1.3 L0.5 消费侧列门禁（v2.3 新增，与 0-A 同批）

**要解决的问题**：台账登记 `severity: 阻断` 之后，**没有任何执行点消费这个标记**。这意味着"每股收益穿越"这件事在工程上是不可见的——直到某天有策略写了 `df["每股收益"]`，穿越立即变成活动泄漏，而 CI 全绿。

**设计**：

| 项 | 内容 |
|---|---|
| 落点 | `myquant/leakage_gate/consumption.py`（纯函数比对，守 L0 分层） |
| 输入 | ① 台账 `severity` 映射（经 `core.config_loader`）；② 策略实际引用列清单 |
| 引用列取法 | **AST 扫描为主**（扫 `df["列名"]`、`df.列名`、`columns=[...]`、字符串常量比对台账键名）+ **契约 `consumed_columns` 声明为辅**；取**并集**，避免声明漏报 |
| 判据 | `实测引用列 ∩ {severity == 阻断} ≠ ∅` → **出口报红** |
| 执行点 | `assert_all_gates_pass` 第 3 步（§5.4），即 `create_engine` / `create_live_engine` |
| 红线 | RL-13（§6.8）；规则 ID R11（§10.2） |
| 豁免 | 需审批（如某列正在修复中、策略有充分理由用保守近似） |
| 反向测试 | **必须**：构造一个引用 `每股收益` 的假策略，断言出口报红（`tests/leakage_gate/test_consumption_gate.py`） |

**为什么这条优先级高于整套静态 AST 扫描**：R02（`center=True`）、R04（`train_test_split`）、R05（`StandardScaler`）经实测**全项目 0 命中**——它们防的是本项目还没犯的错。而 R11 防的是**本项目已经犯了、且只差一次引用就会引爆的错**。成本上，R11 只需一个纯函数 + 台账 severity + AST 列名扫描；R03 却需要"调用链维度分析"（§10.4）才能区分截面与时序。

### 10.8 R11 — 消费侧列门禁（v2.3 新增）

**动机**：`每股收益` 的穿越已确证（R09 命中 4 处），但该列**当前零消费方**：

- ML 特征白名单 `myquant/ml/features.py:82-89` `BAR_CN_COLUMN_MAP` 仅含 `open/high/low/close/volume/amount`，输出列 `BAR_CN_COLUMNS`(`:93-94`) 另加 `timestamp` 与 `trades`，**不含每股收益**；`CN_REQUIRED_COLUMNS`(`:91`) 仅 `开盘价/最高价/最低价/收盘价`；
- `myquant/strategies/` 全目录检索 `每股收益|eps` **零命中**。

因此该缺陷当前是**休眠**的：parquet 里有穿越值，但未污染任何已产出的回测或训练结论。它的危险在于**引爆成本极低**——把 `每股收益` 加进 `BAR_CN_COLUMN_MAP` 只需一行代码，加完 CI 全绿、回测照跑，而结果已被未来财报信息污染。

**规则定义**：

| 项 | 内容 |
|---|---|
| 模式 | 策略/因子/特征代码实际引用的数据列 ∩ 台账 `{severity: 阻断}` ≠ ∅ |
| 列引用取法 | AST 扫描（`df["列名"]`、`df.列名`、`columns=[...]`、字符串常量比对台账键）**∪** 契约 `consumed_columns` 声明。取并集，防声明漏报 |
| 档位 | **阻断** |
| 执行点 | `assert_all_gates_pass` 第 3 步 → `create_engine` / `create_live_engine`（§5.4） |
| 数据源 | `config/data_time_semantics.yaml` 的 `severity` 字段（经 `core.config_loader`） |
| 命中数 | **当前 0**（无消费方）——**这不是"空转规则"**：R02/R04/R05 的 0 命中意味着"防的是本项目不会犯的错"；R11 的 0 命中意味着"防的是本项目已经埋好、只差一次引用就引爆的错" |
| 白名单 | 豁免须写明理由 + 有效期（如"修复期内临时使用保守近似"），落 `exemption.py` |
| 反向测试 | `tests/leakage_gate/test_consumption_gate.py`：构造引用 `每股收益` 的假策略，断言出口报红 |

**与 R10 的关系**：R10 管"列有没有登记"（供给侧元规则），R11 管"登记的阻断列有没有被用"（消费侧执行点）。两者互补，**缺一不可**——只有 R10 时，台账是一份没人读的报告。

**扩展价值**：R11 天然覆盖未来任何新增穿越列。新列一旦在台账标为 `severity: 阻断`，全项目即刻禁止引用，无需为每个新缺陷单写规则。
