### 2.2 修正项（4 处，均基于实测）

**修正 1 —— K1 证据链：ann_date 断点比 CSV 链路更上游（直接断在财务取数接口的字段映射）**

- v1.0 的证据链是：`FINANCIAL_CSV_COLUMNS`（17 列无 ann_date）→ CSV 全量重写丢列 → 回灌 replace 置 NULL。
- 实测修正：当前库 `financial_data` 的 `data_source` **全部是 `akshare_eastmoney_datacenter_history`**（东财数据中心历史财务接口），`created_at` 全部集中在 2026-09-30（一次性导入），**没有任何一行来自 CSV 链路**。
- 直接断点在 `sources/akshare_source.py` 的财务记录构造：东财估值（`:867-879`）、新浪摘要（`:921-929`）、东财历史（`:1057` 附近）三处构造的 dict **均无 `ann_date` 键**，全文件 grep `ann_date/公告日期/发布日期` **零命中**——即**上游接口映射根本没取公告日期字段**，下游 `financial_service.py:286-289`（`raw.get("ann_date")` → None）、`time_semantics.py:89-95`（回退 deadline）依次级联。
- 影响：修复点要**同时**落在两处——① 财务取数接口映射补公告日期字段（新施工项，见 §5 B-09）；② CSV 列清单补 `ann_date`（v1.0 的 A-04 保留，作为第二供给链）。只修 CSV 链路无法让存量与增量数据获得 ann_date。

**修正 2 —— K2 精确化：被策略消费的财务派生量只有"流通股本"一个**

- v1.0 表述："真正被策略消费的三个财务派生量（流通股本/换手率/市盈动）"，并引用 `multi_factor_strategy.py:169,730` 作为换手率消费点。
- 实测：`multi_factor_strategy.py:166,169,696,728,730` **全部指向"流通股本"**（`consumed_columns=["收盘价","成交量","流通股本"]`）；全局 grep `turnover/pe_dynamic` 消费点仅命中写入端（`manager.py:862,1097`、`full_clean_service.py:1079`、`derived_metrics.py:224,251`）与 `ml/training_pipeline.py:526` 的无关训练指标 → **换手率/市盈动在消费侧零命中**（与台账 `:69,:79` consumers=`[]` 一致）。
- 修正后的结论（K2 核心不变，表述更准）：**唯一被策略消费的财务派生量（流通股本）仍走 `report_deadline_estimate` 推定口径、代码看不到 `ann_date`；PIT 统一落点只覆盖了零消费的每股收益**。换手率/市盈动虽当前零消费，但作为 processed 常驻列，任何未来消费都无 PIT 保障 → B-07 施工范围不变（三列统一收敛），优先级依据"流通股本在消费路径上"。

**修正 3 —— P0-6K 现状更新：引擎已 fail-closed，schema 分叉是潜伏风险而非已发生**

- v1.0（基于 10-02 基线）称："`vectorized_engine.py:597-602` 只校验列存在性、不校验 NaN → 涨跌停校验静默失效"。
- 实测（当前代码）：`vectorized_engine.py:597-601` **已改为列缺失即 raise（fail-closed）**，注释标明 P1-10 换源 data_col；`provider.py:799-800` 读侧在整列缺失时兜底派生 `前收盘价`；`mixed_engine.py:946` 有同样兜底。
- 实测（当前磁盘）：3,195 个 parquet **全库无 `前收盘价` 列**（15 列模板产物）→ 引擎依赖 provider 读侧派生，当前可正常供给。
- 修正后的残留风险（仍须施工）：**部分 NaN 静默路径**——若全量导出（会产 16 列）先跑、增量合并再跑（`manager.py:1359` `reindex(columns=existing_df.columns)`），增量新行 `前收盘价` 为 NaN 且整列存在 → provider 不再派生 → 引擎只查列存在不查 NaN → pre_close 数组含 NaN → 涨跌停比较恒 False。此路径未被当前磁盘触发，但**代码级必然**（一旦两写入方按序执行）。
- 施工调整：A-09（列模板对齐）保留并升为"必做"；V-11（重导不抹除）从"待验证"改为"施工后回归门禁"。

**修正 4 —— `backups/processed_6col_20261002/` 归档目录当前不存在**

- v1.0 称"6 列残留 2,376 个已归档至 `backups/processed_6col_20261002/`"。实测 `backups/` 仅含 `tencent_hfq_orphans_20261001_225848.csv`，无该归档目录。
- 处理：不否定 v1.0 当时的归档动作（可能事后清理），但**当前磁盘无该证据**。本版将"6 列残留归档"从现状描述中移除，改为施工项 A-13 的配套动作（见 §5）。

### 2.3 新增发现（2 处，v1.0 未覆盖）

**新增 1 —— DWS 因子层空转（`factor_data` 0 行、`features/` 空目录）**

- 实测：`factor_data` 表 0 行、0 标的；`datasets/features/` 仅 `.gitkeep`（计数=1）；`datasets/models` 1 项、`live_state` 12 项。
- 含义：v1.0 把 `datasets/features/` + `factor_data` 表视为"DWS 服务层（因子/特征产出，供策略与 ML 消费）"，但**该层当前没有数据**。因子计算要么只发生在内存（策略侧现算），要么从未落库接线。这直接改变 §3 目标结构的 DWS 段设计——本轮**不需要**为 DWS 设计门禁（无数据流经），而应先把"因子落库/不落库"作为决策项（施工项 C-09），避免为空气设计门禁。

**新增 2 —— 重复行 4,377 个是"已发生事实"，且机制被 3 行样本实证**

- v1.0 将"UNIQUE 失效产生重复行"列为推导（P0-4 待 V-01 验证）。实测不仅确认 4,377 个重复键，还从 `000001.SZ` 的 3 行样本看清机制：`tdx` 原始下载行（created 2026-10-16 00:20）+ 两行 `incremental_clean`（created 09:20 / 09:25，同一天增量清洗跑了两次，每次各插一行）→ **增量清洗的 `INSERT OR REPLACE` 因 UNIQUE 对 NULL 失效而无去重能力**（`queries.py:212` 的 REPLACE 需命中唯一约束才替换）。
- 施工影响：B-01（部分唯一索引）从"可选"升级为 **P0 必修**；且需新增一次性去重清理（施工项 A-13），否则建唯一索引会直接失败。

## 4. 结构优化设计（基于实测修订）

### 4.1 设计总则（沿用 v1.0，5 条不变）

1. 不做物理重构（16.9M 行迁移风险 > 收益）。
2. 每层只做一件事，门禁放在数据流上游。
3. 规则必须落地留痕（否决/放行都要可举证）。
4. 一次只改一件事，每一刀可逆。
5. 尊重新账与旧账：不追溯重写历史行；存量按专项校验决定回填。

### 4.3 关键机制设计（沿用 v1.0 的 a–f，按实测修订）

#### (a) 统一写入口 MarketDataWriter（收敛 3 条 DB 写路径）

- `write_raw`：过门禁①结构校验 + 打 `ingest_time`，写入原始事实行。
- `write_cleaned`：UPSERT 语义按 `(symbol, trade_date)` 更新，绝不删除；旧值写入 `correction_ledger`。
- 配套（实测驱动的关键修订）：
  - **A-13 前置**：清理存量 4,377 个重复键（保留最优行：优先 tdx/tencent_http 原始行 > incremental_clean；同源保留 created_at 最早），然后建部分唯一索引。
  - 修复 `UNIQUE`：部分唯一索引 `WHERE trade_time IS NULL`（SQLite 支持）。
  - 消除嵌套事务：`connection.transaction()` 加 SAVEPOINT 或让 `DataQueries` 方法接受"调用方已开事务"标志（**K3 根因，P0 必做**）。
  - 修正 `needs_write = True or (...)` 恒真式（`full_clean_service.py:592`，1 行）。
  - 移除 `manager.py:867-868` 异常吞噬。

#### (b) 修正台账 Correction Ledger（落地 v2.0 §7.2）

同 v1.0 设计不变（symbol/trade_date/field/old_value/new_value/corrected_at/corrected_by/reason）。

#### (c) 三时间戳采集元数据（落地 v2.0 §5.3）

`ingest_time` / `ingest_batch` / `anomaly_flags`（`source_name` 复用 `data_source` 并统一命名规范）——解决 P0-1 标记丢失、P0-6 溯源断裂、P1-1 无 system_time。

#### (d) 门禁①：入库前准入（新增）

`admission.py`：BLOCK（必需字段缺失/类型不可转/high<low/负价/空 symbol/时间戳无效）/ FLAG（价格跳变、量异动、缺失行、源切换 → 写 `anomaly_flags`）/ PASS；白名单 `admission_whitelist.yaml`（生效窗 + 双签 + 审计哈希链）。实测修订：门禁①的 FLAG 字段要**真正落到 `anomaly_flags` 列并随行入库**（当前 `_warnings` 被丢弃是 K4 的核心失败点）。

#### (e) 阈值配置化与分品种（落地 v2.0 §9）

`data_clean.yaml` 扩展两级阈值（default + by_market + by_symbol）。实测口径：当前单一 0.22 对主板（10% 涨跌停）放过 2 倍异常、对北交所（30%）误杀合法涨停——分品种是口径回归而非精细。

#### (f) 停牌硬阻断（P1-3）

- processed 模板纳入 `is_suspended`（或 DWD 现算 volume==0）；
- `tradability.py:181-192` 的 `rules_skipped` 升级为结构化告警 + 可配 fail-closed 拒单；
- 生产入口不再传 `is_suspended=None`（`make_suspended_lookup` 已存在，只需接线）。

#### (g)【新增】DWS 因子层落库决策（C-09）

- 实测 `factor_data` 0 行 → 先决策"因子是否落库"：若落库 → 接线 `factor_sync_service` 并补口径版本绑定；若不落库 → 更新文档（数据字典/架构图）把 DWS 明确为"processed + DB 派生列组合，因子在内存现算"，移除对 `features/` 的引用。**不做决策则禁止为 DWS 设计门禁**（避免为空气设计）。

## 9. 结论与建议

### 9.1 结论（实测驱动）

1. **v1.0 的方向与优先级经受住实测核验**：K1/K3/K4 的机制全部确认；且 K1（ann_date 全 NULL）、P0-4（4,377 重复）已从"潜在风险"升级为"已发生事实"。**施工优先级成立，且更紧迫。**
2. **K1 的修复点必须上移一格**：直接断点在 `akshare_source.py` 财务取数映射（不取公告日期字段），CSV 列清单只是第二断点。只按 v1.0 修 CSV 链路，ann_date 依然全 NULL。
3. **K2 的表述精确化后施工范围不变**：被消费的财务派生量实为"流通股本"一个（多因子策略），换手率/市盈动零消费但无 PIT 保障——三列统一收敛到 `eff_disclosure_date` 仍是 B-07 的正确范围。
4. **磁盘现状比 v1.0 基线更干净也更脆弱**：parquet 全库 15 列（无前收盘价）且引擎已 fail-closed（P1-10 已修复部分），但"16 列全量产物 + 增量 reindex → 部分 NaN 静默"的代码级路径仍在 → A-09 是必修而非可选。
5. **两个 v1.0 未覆盖的事实改变设计范围**：DWS 因子层 0 行（先 C-09 决策再谈门禁）；backups 归档目录不存在（A-13 配套）。

### 9.2 优先级建议（若只能做三件事）

1. **A-13 + B-01（清重复 + 唯一索引）** —— 4,377 个重复键**已发生**，正在污染回测与实盘消费；不清重复，后续一切 UPSERT 语义都不可信。
2. **A-02 + B-09 + A-04（修 K1：取数补公告日 + CSV 补列）** —— ann_date 全库 100% NULL，整套 PIT 治理实质失效；修复点已上移确认。紧随 **B-07** 让被消费的流通股本收敛到统一落点。
3. **A-03 + A-05（修 K3：嵌套事务）** —— 封堵"标的被删空且不可回滚"窗口；与 A-08（orders 残量）、A-09（前收盘价潜伏分叉）同属"静默损坏类"，打包一次做完。

### 9.3 最值得记住的一点（实测强化）

v1.0 §11.3 总结的失败模式在本轮实测中再次得到印证，且多了一个变体：**能力被实现 → 接线断在最后一米 → 测试只验存在不验生效**。PIT 治理（成果落在零消费字段 + 取数不取公告日）、版本管理（hasattr 断言）、阈值配置化（yaml 无键）均属此类。**本版施工的验收标准全部要求"可观测的行为变化"**（如"新导入行 ann_date 非空率 > 90%"、"清理后重复键 = 0"），而不是"接口存在"。

### 9.4 最后一句

> 实测把 v1.0 的"应当担心"变成了"必须处理"：ann_date 已经不是"可能被清空"，而是**全库 0 非空**；重复行已经不是"理论上可能"，而是**4,377 个已入库**。结构优化的顺序因此更清晰——**先清账（去重 + 补披露日）、再立契约（唯一索引 + 写入口 + 门禁）、后上闸门（FLAG/BLOCK 生效）**，每一步都以可观测的行为变化验收。
