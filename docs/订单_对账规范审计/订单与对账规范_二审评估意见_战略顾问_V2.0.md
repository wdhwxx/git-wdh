## 3. 二审增量：原报告与一审共同漏掉的机制

### 3.1 【最重要】零容差 × 300 秒镜像 = 自持式假冻结循环（原报告未识别）

**这不是一个新 bug，而是 RC-01、RC-02、RC-11、RC-14、RC-44 五条缺陷的**闭环耦合**，其后果比"单次清空账本"更隐蔽：系统会进入**永久冻结—解冻—再冻结**的循环，且每次循环都销毁证据。**

逐步推演（每步附行号）：

```
① 本地现金在 LIVE 下由成交回调维护：
   portfolio.apply_trade → _cash -= (amount + commission)        [portfolio.py:1006-1011]
② 券商现金按日终结算/冻结规则变动：
   券商现金 ≠ 本地按成交累加的现金
   → cash_diff = self._cash - broker_cash → 非零                [portfolio.py:695-696]
③ 容差 = 0（LOCKED）→ abs(cash_diff) > 0 成立
   → 告警 + 冻结 + pause（禁开仓）                              [portfolio.py:125-129, 729-776]
④ 同一笔差异在下一次实时核对/异步核对中被再次发现，
   但 _frozen 已为 True → 不再触发新告警（仅首次冻结告警）        [account_reconciler.py:246-257]
⑤ ≤300 秒后，周期巡检执行 _broker_accountability_patrol
   → portfolio.sync_from_broker(broker)
   → 差异超阈只记 log，**紧接着** _cash = broker cash
     、_positions.clear() + 按券商重建                          [engine.py:2242 → portfolio.py:811-836]
⑥ 本地现金**被改写成券商现金** → 差异归零
⑦ 但冻结标记仍在（内存态），且**无生产解冻入口**
   （mark_resolved 无调用方、/api/risk/resume = 501）           [account_reconciler.py:352；routes.py:693-699]
   ⇒ 系统停在"已冻结 + 差异已归零"的矛盾态
⑧ 下一笔成交 → 本地现金再次偏离券商现金 → 回到 ②
   ⇒ **永久循环**；且每次循环都把本地账本证据覆写一次
```

**为什么这比原报告描述的更严重**：
- 原报告把 RC-01 描述为"差异被抹平"，把 RC-11 描述为"浮点噪声即冻结"，把 RC-14 描述为"无解冻入口"——这是**三条独立条目**。
- 二审发现它们是**同一条自持回路**：**镜像动作既是"抹平差异的凶手"，又是"解冻之后的复燃源"**。这意味着：
  - 即便按阶段 0 修好 RC-01（禁重建），回路会退化为"差异永久存在 + 永久冻结 + 无解冻入口"→ 系统**停摆且无法恢复**（比现在更危险，因为它不再自我抹平，也就不会"看起来正常"）；
  - 若只修 RC-11（分位取整）而不修 RC-01/RC-14，回路的**触发阈值**从 1e-9 抬高到 0.01 元，循环依然存在，只是频率下降。
- **施工含义（必须写进方案）**：**RC-01、RC-11、RC-14 必须同批修复**，单独修任一条都会把一个"静默污染"问题转化为"系统不可用"问题。这条依赖关系原报告与一审**都没有标出**。

### 3.2 【重要】原报告定级未区分"当前形态"与"最坏形态"（对施工排期影响最大）

原报告 §8 与一审 §4.4 都讨论了形态，但**都没有回到配置事实**。二审实测：

| 事实 | 证据 | 含义 |
|---|---|---|
| 交付配置 `trade_mode: paper` | `config/live_config.yaml:16` | 默认不发真单 |
| 交付配置 `broker.type: paper` | `config/live_config.yaml:30` | **默认不接 QMT** |
| 示例配置才指向 QMT | `config/live_config.example.yaml:33,40`（`type: qmt` / `mode: SIM`） | QMT 是"未来切割目标"，不是当前形态 |
| `broker.type` 是**单一键** | 同上 | 上真钱 = **改 2 个配置键 + 显式 `--mode live --confirm-live`** |

**结论**：`enable_resend_pending` 默认 False（`scheduler.py:1664`）、`broker.type=paper`（`live_config.yaml:30`）这两项，使 **RC-13（事件回调同步对账阻塞）与 RC-22（断线不补发）在当前交付配置下不触发**；`enable_scheduler` 默认 True（`engine_assembly.py:264`），使 **RC-52（装配静默降级）当前不触发**。

→ 这三项的**定级应标注"条件触发"**，而不是与 RC-01/02/16 并列 P0。**这正是"资源有限时先打哪里"的决定性输入**，一审的 §4.4 说对了方向，但**用错了依据**（它凭"只用 QMT 单券商"的假设，而事实是当前连 QMT 都没接）。

### 3.3 【重要】一审 §4.1 的修复建议方向错误，若照做会把缺陷制度化

一审主张：T0-1 禁重建后必须保留"差异未超阈时的定期镜像"，否则本地账会因长期不镜像而缓慢漂移。

**二审反对，理由有三**：

1. **概念错位**：本地账本在 LIVE 下**本就不应等于券商账本**——它由成交/订单回调事件维护（`portfolio.apply_trade`、`qmt_broker._execute_fill`）。"定期用券商值覆写本地值"不是"镜像收敛"，而是**删除本地记账证据**。券商值只在**结算后**才具有账本权威性，盘中它只是"另一个数据源"。
2. **一审的建议会让 RC-11 永远无法自愈**：零容差下，"未超阈"意味着两值已相等；若长期未超阈，说明本地记账**本就与券商一致**，根本无需镜像；若已超阈，则该路径按 T0-1 被禁。**"需要镜像时不能用、能用时不需要"** ——这条建议在逻辑上自相矛盾。
3. **保守替代方案（二审建议）**：
   - **双值并存**：portfolio 同时保存 `book_cash`（本地记账结果）与 `broker_cash`（快照观测值），**只比对、不覆盖**；
   - **收敛走补偿，不走覆写**：差异修复 = 依据 `fills` 账本**重放/补偿**（阶段 1 后具备该能力），或在**显式裁定**下执行 `adopt_broker_ledger(reason, actor)` 并落库审计（原报告 T3-3 已给出正确形态）；
   - **删除"定期镜像"这个概念**，代之以"**对账快照留存**"（每 300 秒记录两侧数值到 `reconciliation_runs`，作为趋势与取证，而非覆写）。

### 3.4 【重要】"零代码止血包"缺少上限约束，且有两条操作风险

一审 §4.2 的意图正确，但作为"资深顾问建议"存在三点硬伤，直接关系真钱安全：

1. **`auto_failover` 无法通过配置关闭**（实测）：`manager.py:146` 构造函数默认 `True`；三处生产调用点 `engine.py:193,467,482` 全部 `BrokerManager()`（取默认值）；只有 `scripts/实时行情驱动.py:188`、`scripts/双券商模拟实盘.py:246` 显式传 `True`。**全仓无任何 config 键绑定 `auto_failover`** → 一审所说"它本身是个开关属性，可以先关掉"**在当前版本不可执行**，除非改代码。
   → **二审修正**：这恰恰**加重**了 RC-16 的严重度（**无配置逃生阀**）。正确止血不是"关 failover"，而是**T0-12：把"未知结果"从 channel 分类中摘出来、不 failover**。关掉 failover 会让"主券商已断线、订单根本没发出"的合法场景失去重试，属于用另一个风险换这个风险。
2. **"先打开告警通道"必须先做链路验证**：`notification.enabled=false` 已存在（`:3395` 段），意味着**从未验证过**该配置路径能真的送达。一审把它当作"打开即可"，但真实风险是"打开后误以为告警可用"。→ **二审修正**：打开后必须**主动触发一条 `reconciliation` 类 CRITICAL 并确认人工端收到**（与 T4-5 装配有效性测试同批），否则等于把 fail-open 从"日志"搬到"配置"。
3. **"先在 paper/sim 跑一轮"会给出虚假信心**：一审自己也指出 RC-19（Paper 双订单簿，`get_orders` 恒空）。在 RC-19 未修复前，**paper 跑一轮无法验证"订单/对账对账链路"**——因为它连订单都读不到。→ **二审修正**：该轮仿真的正确目的应明确限定为"验证行情→信号→撮合→持仓"，**订单/对账链路的验证必须在 RC-19 修复后重跑**。"零代码止血包"的第三条应改为"**先修 RC-19，再跑仿真**"。

### 3.5 【新增缺陷】failover 复用同一订单副本，第 2 个备券商必然失败

- **证据**：`manager.py:619`（克隆在循环**外**）→ `:622-633`（循环内复用 `retry_order`）→ `:630`（提交同一对象）→ `:634`（`_is_order_rejected` 判定）→ 首个备券商拒单后该对象进入 `REJECTED` 终态（`models/trade.py:92-99`）→ 第 2 个备券商调 `_submit_order_impl` 时 `order.submit()` 失败（`qmt_broker.py:594-599`）。
- **后果**：注册 ≥3 个券商时，failover 链**实际只有第一个备券商可用**；而 `_failover_stats` 会记为"全部失败"并进入 60 秒冷却（`manager.py:644-647`），掩盖真实原因。现有测试（`test_broker_manager_failover.py`）只覆盖"主 + 1 备"，**结构上看不到该缺陷**。
- **归属**：属原报告 RC-16 的次生缺陷（一审与五路子审计均提及"复用副本"但**未指出其必然失败**）。**定级 P2**（多券商形态才触发，且当前配置为 paper 单券商），但**修复成本极低**：把 `:619` 的克隆移入循环体。

## 4. 对一审 §4.4"单 QMT 只咬 7 项"的校准

一审左列 7 项缺了 **RC-04**——它正是"单 QMT 真钱"场景的**必咬项**：

- `qmt_broker.py:760` 用 `asset.cash`（**含冻结**）充当 `available`，再于 `:763` 用它判"资金不足"；
- 而同一文件 `:941-943` 自己定义了 `available_cash = cash - frozen_cash`；
