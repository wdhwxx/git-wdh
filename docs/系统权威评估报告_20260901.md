## 二、高危问题（2 项，均在实盘域）

### 🔴 H1：实盘入口 `run_实盘入口.py` 双重断链——永远无法真正启动实盘引擎

**位置**：`run_实盘入口.py:211-278`

问题由两个叠加的缺陷构成：

1. **引用不存在的符号**：第 213 行 `from myquant.core.config_loader import load_config`。经核验 `myquant/core/config_loader.py` 只定义了 `ConfigLoader` 类及其 `load()` 方法，**不存在 `load_config` 函数**。该 `ImportError` 使代码永远落入第 215 行 `except` 分支，打印“阶段0提示：myquant.live 实盘引擎尚未实现”并返回 0。
2. **误导性后果**：`myquant.live.engine.LiveEngine` **实际已完整实现**（1456 行），但入口因上述引用错误永远认为它“尚未实现”。用户执行 `python run_实盘入口.py` 会得到一条**与事实相反的提示**，且无任何报错，极易误判系统状态。
3. **即使修复第 1 点，第 278 行 `LiveEngine(config=config)` 仍会 TypeError**：`LiveEngine.__init__`（engine.py:171）的签名为 `(risk_config, engine_id, realtime_poll_interval, warmup_bars, enable_warmup)`，不接受 `config` 参数。

**影响**：实盘入口 100% 不可用；且以“尚未实现”的假象掩盖真实缺陷。

### 🔴 H2：实盘引擎未接入风控核心与全部实盘保障组件——实盘保护机制整体旁路

**位置**：`myquant/live/engine.py`（全文）

经全文检索核验，`LiveEngine` 内部**没有任何**对以下组件的引用：

| 组件 | 职责 | 状态 |
|---|---|---|
| `risk/risk_manager.py` RiskManager | 分级风控、数据质量暂停、规则库 | ❌ 未导入未调用；引擎仅内置一个简化版 `_risk_check()`（仅查资金/仓位） |
| `live/state_store.py` StateStore | 崩溃恢复、状态持久化 | ❌ 未接入 |
| `live/scheduler.py` LiveScheduler | 定时任务、盘前盘后 | ❌ 未接入 |
| `risk/guardian.py` RiskGuardian | 健康守护、强制平仓 | ❌ 未接入 |
| `monitoring/alerting.py` AlertManager | 告警通道 | ❌ 未接入 |
| `monitoring/metrics_collector.py` | 运行指标采集 | ❌ 未接入 |

**影响**：交接文档铁律2（回测→实盘无缝对接、风控共用）与入口脚本自述的“安全机制”（每笔订单提交前强制风控检查、状态持久化崩溃恢复）**在实盘引擎层全部落空**。`risk_manager.py` 精心实现的 3 个数据质量事件订阅、`guardian.py` 的强制平仓决策，在实盘运行时没有任何触发路径。这是本项目当前最严重的架构断链。

## 三、中危问题（6 项）

### 🟡 M1：绩效计算去重缺陷导致总收益归零（已被测试证实）

- **位置**：`myquant/backtest/metrics.py:379-383`（`_equity_to_df`）
- **机理**：净值曲线按 `date` 字段去重；而 `EquityPoint.date` 默认为空字符串（`models/backtest.py:381`）。当调用方不填 `date` 时，全部数据点被去重为 1 行，`total_return` 恒为 0。
- **证据**：`tests/unit/test_backtest.py::test_total_return_positive` 实际运行失败——10% 收益的曲线算出 `ret=0.00%`。这是全项目唯一失败的测试，属确证 BUG。
- **影响面**：主回测链路是否触发取决于 `recorder.py` 记录净值时是否填充 `date`；但任何复用 `MetricsCalculator` 的外部调用（报告脚本、实盘绩效）都有归零风险。

### 🟡 M2：数据管理器保存路径未启用跨批次去重

- **位置**：`myquant/data_access/manager.py:848`
- **问题**：`clean_and_save_symbol()` 调用 `_save_processed_data()` 时未传 `deduplicate_with_latest=True`（该参数默认 `False`，见 manager.py:1040）。`#O3修复` 注释声明的跨批次去重能力在当前所有调用路径中均不生效，增量更新场景可能向 processed 写入与既有数据重复的记录。

### 🟡 M3：数据获取器“三级缓存”名实不符

- **位置**：`myquant/data_access/fetcher.py`
- **问题**：注释与交接文档声称“三级缓存：内存→文件→数据库”，实际只实现了内存缓存（`_MemoryCache`），全文无任何文件/数据库缓存读写路径。文档误导，且跨进程复用场景下缓存静默失效。

### 🟡 M4：API 层依赖注入完全断开——`get_services.py` 整体是死代码

- **位置**：`myquant/api/routes.py` 与 `myquant/api/dependencies/get_services.py`
- **问题**：`routes.py` 全文未导入 `get_services.py`，服务获取全部走闭包内硬编码懒加载；`get_services.py` 定义的 `ServiceContainer` 与 6 个依赖注入函数无任何调用点。

### 🟡 M5：两条清洗入口接口不统一

- **位置**：`scripts/数据清洗.py:41` 与 `scripts/数据全量清洗.py`
- **问题**：增量清洗走 `cleaner.pipeline.run_clean_pipeline()`（纯函数），全量清洗走 `full_clean_service.FullCleanService`（含 DB 事务写回 + 元信息记录）。两条链路能力不对等（增量清洗不落清洗元信息），后续只维护其一将导致另一条静默失效。

### 🟡 M6：交易统计口径偏差

- **位置**：`myquant/backtest/metrics.py:227`（`_calc_trade_metrics`）
- **问题**：平仓筛选条件 `t.pnl != 0 or t.side == "SELL"` 会把所有卖出记录计入交易次数（含未配对场景），胜率/盈亏比口径与标准 round-trip 统计不一致，存在虚高风险。

### A.1 对 H1（实盘入口断链）的说明：降级为"阶段性遗留"，但仍是事项1的硬路障

**文档提供的背景**（支持修正定性的部分）：

**但问题依然成立，且文档让后果更清晰**：

1. 文档的"恢复入口"（第63行）要求将来联调时执行 `python run_实盘入口.py` 做小额验证。而实测该文件第213行引用的 `load_config` 函数**在 `myquant/core/config_loader.py` 中不存在**，入口永远落入"尚未实现"的假提示分支——**券商环境就绪后，按文档操作也永远到不了真实启动代码**，且没有任何报错，只有误导性提示。

**修正后定性**：不是"当前阻塞"（现在本就不跑真钱），而是**事项1第一张检查清单的必踩地雷**——不先修它，文档规划的联调流程走不完第一步。

### A.3 交叉核对中的两个附带发现
