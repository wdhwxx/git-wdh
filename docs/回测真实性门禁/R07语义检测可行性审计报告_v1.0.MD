## 一、背景

### 1.1 R07 是什么

R07 是回测真实性门禁体系中的一项运行时校验规则，原始定义为：

> **横截面 as-of 校验**：选股池/因子排名时，检测是否对含未来行的切片做了 rank/quantile。

**原始缺陷**（v2.1 方案）：
- R07 仅实现为"警告档"（severity=warning），出口断言从不消费 severity → 实际不阻断
- 校验逻辑是"升档"（把警告升级为阻断），但未解决"如何识别含未来行的 rank"的核心问题

### 1.2 v2.2 的修正方向

方案文档 §2.3 缺陷 C（L173）明确指出：

> R07 的正确处理不是"升档"，而是**改写为语义检测**（是否对含未来行的切片做 rank/quantile）或明确降级为报告项。

## 二、现状调研

### 2.1 已有机制

| 机制 | 位置 | 覆盖范围 |
|---|---|---|
| P0-07 因果切片 | `StrategyContext.get_data()` 返回 `index <= current_bar_ts` 切片视图 | 结构上保证策略只能通过 `context.get_data()` 看到过去数据 |
| LightLookaheadGuard `check_data_access` | `light_lookahead_guard.py:312` | 运行时校验数据访问时刻（data_ts <= current_ts） |
| LightLookaheadGuard `check_indicator_window` | `light_lookahead_guard.py:344` | 校验指标计算窗口是否含当日数据 |
| LightLookaheadGuard `check_signal_execution` | `light_lookahead_guard.py:396` | 校验信号成交时序（trade_date > signal_date） |

### 2.2 R07 的盲区

现有机制覆盖了"数据访问"和"指标窗口"，但**不覆盖以下场景**：

```python
# 场景 A：绕过 get_data，直接用全量 df
df = context.data["000001.SZ"]  # 全量历史（含未来）
rank = df["close"].pct_change(20).rank()  # 全量排名 → 含未来数据
```

```python
# 场景 B：as_of 截断后做横截面排名
pool = pool_builder.build(all_symbols, context.data, as_of=bar.timestamp)
# pool_builder 内部已按 as_of 截断，但外部若对 pool 再做 rank/quantile，
# 如何确认 pool 真的不含未来行？
```

**R07 语义检测的目标**：识别上述场景中的"含未来行的 rank/quantile"。

## 三、三种实现方案对比

### 方案 A：静态 AST 扫描策略代码

**原理**：解析策略源码 AST，识别 `df.loc[:as_of].rank()` 模式，判断是否在切片后做了排名。

**优点**：
- 不侵入运行时，零性能开销
- 可在 CI 阶段自动检查

**缺点**：
- 误报率高：动态生成的 df（如 `df = load_data(symbol)`）无法静态识别
- 漏报率高：策略若用 `df[df.index <= as_of]` 替代 `.loc[:as_of]`，AST 扫描无法识别
- 维护成本高：策略写法多样，需要不断补充 AST 模式

**改动量**：约 200~300 行 AST 扫描器

**风险**：⭐⭐⭐（误报率高，现有策略可能全部变红）

---

### 方案 B：运行时 monkey-patch pandas

**原理**：hook pandas 的 `rank()` / `quantile()` 方法，调用时检查 df 的 max index 是否 > current_ts。

**优点**：
- 运行时精确检测，覆盖所有 rank/quantile 调用
- 不依赖策略写法

**缺点**：
- 侵入性强：monkey-patch pandas 全局方法，可能与其他库冲突
- 性能开销：每次 rank/quantile 调用都要检查 max index
- 误报率高：合法的滚动窗口 rank（如 20 日动量排名）也会被误报——因为滚动窗口的 df 本身不含未来行，但 max index 可能 > current_ts

**改动量**：约 150~200 行 hook + 异常处理

**风险**：⭐⭐⭐⭐（侵入性强，误报率高，性能风险）

---

### 方案 C：因子层手动声明

**原理**：要求策略在计算因子时，手动声明"本因子是否含未来行"（类似 `@factor_declare(lookahead=False)` 装饰器）。

**优点**：
- 实现简单，零侵入
- 误报率为零（策略自觉声明）

**缺点**：
- 回到 v2.1 的老路："委托而非保证"，依赖策略自觉
- 与 P0-07 因果切片的设计初衷（结构保证）矛盾
- 无法检测"忘记声明"的情况

**改动量**：约 50~100 行装饰器 + 文档

**风险**：⭐（实现简单，但设计倒退）

## 四、关键依赖：P1-14 豁免通道

方案文档 L911 明确规定：

> **P1-14（豁免）必须先于 P1-07 中 R07 相关处置完成**——为合法截面/滚动对照实现提供豁免通道。

**P1-14 当前状态**：未开工。

**豁免通道的必要性**：

合法策略中存在大量"横截面 rank"场景：

| 场景 | 示例 | 是否含未来行 |
|---|---|---|
| 20 日动量排名 | `groupby(date)["momentum"].rank()` | **否**（滚动窗口已截断） |
| 行业中性化 | `groupby([date, "industry"])["factor"].rank()` | **否**（横截面排名当日截面） |
| 多因子打分 | `rank(factor1) + rank(factor2)` | **否**（当日截面排名） |

如果 R07 语义检测没有豁免通道，上述合法场景会被误报为"含未来行"，导致现有策略全部阻断回测。

## 五、实施建议

### 5.1 短期（当前 P1-07 范围内）

**建议**：**不实施 R07 语义检测**，保持 R07 为"报告项"（仅记录不阻断）。

**理由**：
1. P0-07 因果切片已从结构上消除大部分风险（策略通过 `get_data()` 只能看到过去数据）
2. P1-14 豁免通道未建，强行做会误报合法策略
3. 三种方案都不完美，需要 PoC 验证

### 5.2 中期（P1-14 建成后）

**建议**：先做 PoC 验证，再决定是否实施。

**PoC 步骤**：
1. 选 1~2 个现有策略（如 ma_strategy / rsrs_strategy）
2. 用方案 B（运行时 hook）做原型
3. 统计误报率：合法 rank/quantile 调用被误报的比例
4. 如果误报率 < 5%，进入正式实施；如果 > 5%，放弃

### 5.3 长期（若 PoC 通过）

**建议**：实施方案 B + P1-14 豁免通道。

**落地顺序**：
1. P1-14 豁免通道（豁免合法截面/滚动对照）
2. LightLookaheadGuard 新增 `check_cross_sectional_rank()` 方法
3. 策略侧接线（或引擎侧自动 hook）
4. 红队测试（构造含未来行的 rank，断言被检测）

## 六、结论

| 维度 | 评估 |
|---|---|
| **技术可行性** | 三种方案都可实现，但各有缺陷 |
| **当前时机** | ❌ 不建议（P1-14 未建，误报风险高） |
| **预期收益** | 防止"绕过 get_data 直接用全量 df"这一罕见模式 |
| **预期成本** | 300~500 行改动 + PoC + 豁免通道 |
| **推荐路径** | 短期保持报告项 → 中期 PoC → 长期实施 |

**最终建议**：**R07 语义检测留后续，待 P1-14 豁免通道建成后，先做 PoC 验证误报率，再决定是否正式实施。**
