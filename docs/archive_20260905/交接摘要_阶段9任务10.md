### 4.2 AlertRule 告警规则配置（新增）

**核心功能**：
- `dirty_type_levels: Dict[str, SeverityLevel]` — 脏数据类型→最低告警级别映射（默认14种）
- `bad_ratio_thresholds: List[Tuple[float, SeverityLevel]]` — 脏数据占比阈值→级别（默认3档：>=50% CRITICAL / >=10% ERROR / >=5% WARNING）
- `level_channels: Dict[SeverityLevel, List[str]]` — 告警级别→通道名称列表（默认：CRITICAL→全部4通道 / ERROR→console+log+email / WARNING→console+log / INFO→console）
- `aggregation_window: float` — 聚合窗口（默认60秒）
- `escalation_time: float` — 告警升级时间（默认300秒）
- `escalation_enabled: bool` — 是否启用升级（默认True）
- `default_level: SeverityLevel` — 默认级别（默认WARNING）
- `min_bad_count_for_alert: int` — 最少脏数据数才告警（默认1）
- `auto_acknowledge_info: bool` — 自动确认INFO级（默认True）

**关键方法**：
- `AlertRule.default_rule()` — 工厂方法，创建默认规则（含全部映射）
- `get_level_for_dirty_type(dirty_type)` — 按脏数据类型获取级别
- `get_level_for_bad_ratio(bad_ratio)` — 按占比获取级别
- `get_channels_for_level(level)` — 按级别获取通道列表
- `should_alert(bad_count, bad_ratio, dirty_type)` — 判断是否应该告警
- `determine_level(dirty_type, bad_ratio, event_severity)` — 综合判定最高级别

### 4.3 AlertAggregator 告警聚合器（新增）

**核心功能**：
- 同一标的+同一脏数据类型在聚合窗口内的多条事件聚合为一条告警
- 避免实盘高频场景下告警刷屏
- 流式支持：实盘逐条事件实时聚合

**内部结构**：
- `_AggregationBucket` 聚合桶：key/symbol/data_type/dirty_type/count/first_seen/last_seen/max_level/total_bad/total_total/errors/source_step
- `bad_ratio` 属性：总脏数据/总数

**关键方法**：
- `add_event(symbol, data_type, dirty_type, severity, bad_count, total_count, errors, source_step)` — 添加事件，返回过期桶（如有）
- `flush(key=None)` — 强制刷新聚合桶（None=全部）
- `cleanup_expired()` — 清理并返回过期桶
- `get_pending_count()` / `get_pending_keys()` — 查询待聚合状态

### 4.6 AlertManager 管理器（增强）

**新增功能**：

1. **智能分级**：

   - `determine_level()` — 综合脏数据类型/占比/事件级别取最高

2. **告警聚合**：
   - `handle_data_quality_event()` — should_alert判断→determine_level分级→aggregator.add_event→过期桶发送

3. **告警升级**：
   - `check_escalations()` — 检查WARNING级超时未确认告警，自动升级为ERROR

4. **发送回调**：

   - `handle_pipeline_complete_event()` — 先flush聚合器→失败→ERROR→质量等级分级
   - `handle_quality_alert_event()` — 直接转发（按alert_level映射）

### 4.7 完整事件→告警链路

```
DataQualityEvent (EventBus发布)
    ↓
AlertManager.handle_data_quality_event()
    ├─ AlertRule.should_alert() → 判断是否告警
    ├─ AlertRule.determine_level() → 综合判定级别
    ├─ AlertAggregator.add_event() → 进入聚合桶
    │   └─ 桶过期 → _send_aggregated_alert()
    │       ├─ 构建聚合Alert（aggregation_count/bad_ratio/details）
    │       ├─ _route_channels() → 按级别选择通道
    │       ├─ 多通道发送（console/log/email/webhook）
    │       └─ _notify_callbacks() → 通知metrics等回调
    └─ 返回None（聚合中）

PipelineCompleteEvent
    ↓
AlertManager.handle_pipeline_complete_event()
    ├─ flush_aggregator() → 发送所有待聚合告警
    ├─ 失败 → ERROR告警
    └─ 质量等级分级 → CRITICAL/ERROR/WARNING/不告警
```

## 六、关键设计决策

### 1. 告警聚合策略
- 采用"时间窗口聚合"而非"逐条告警"，避免实盘高频脏数据刷屏
- 聚合桶key = symbol:data_type:dirty_type，同一标的同一脏数据类型聚合
- 聚合窗口可配置（默认60秒），实盘可根据行情频率调整
- 流水线完成时自动flush，确保所有待聚合告警都发送
- 聚合告警包含完整统计：事件数/总脏数据/总数/bad_ratio/最高级别/错误列表

### 2. 智能分级策略
- 综合3个维度取最高级别：脏数据类型映射 + 占比阈值 + 事件本身级别
- 脏数据类型映射覆盖14种已知类型（OHLC逻辑错误/负价格→ERROR，价格跳变→WARNING等）
- 占比阈值3档：>=50% CRITICAL / >=10% ERROR / >=5% WARNING
- 未匹配任何规则时使用默认级别WARNING
- min_bad_count_for_alert防止单条偶发脏数据触发告警

### 3. 告警升级策略
- 只升级WARNING级（ERROR/CRITICAL已经够严重，不需要升级）
- 升级条件：超过escalation_time未确认且未解决
- 升级后创建新的ERROR级告警，标记escalated_from和parent_alert_id
- 原告警自动标记为已确认（避免重复升级）
- 升级检查由scheduler定期调用（任务22），也可手动调用
- 可通过escalation_enabled=False禁用

### 4. 多通道路由策略
- 按AlertRule.level_channels映射，不同级别走不同通道组合
- CRITICAL→全部4通道（console+log+email+webhook）
- ERROR→console+log+email
- WARNING→console+log
- INFO→console
- 通道自身还有min_level过滤，双重保障
- 规则中未配置的通道回退到所有可用通道

### 5. 防未来函数（铁律4）
- 告警只响应已经发生的事件（DataQualityEvent/PipelineCompleteEvent）
- 不使用任何预测模型推断未来可能发生的异常
- 聚合只基于已收到的事件，不预加载未来数据
- 升级只基于已存在告警的确认状态，不预测是否会被确认
- 告警时间戳为事件发生/接收时刻的当前时间
- 源码中无predict/forecast/future关键词

### 6. 为实盘无缝对接预留
- 流式聚合：实盘逐条脏数据事件实时聚合，不刷屏
- 多通道：实盘可配置邮件+钉钉+飞书告警，CRITICAL级多通道并行
- 告警升级：严重问题未及时处理自动升级，确保运维响应
- 发送回调：metrics_collector/risk_manager可注册回调，告警联动
- flush_aggregator：收盘/流水线结束时强制发送所有待聚合告警
- check_escalations：scheduler定期检查升级
- Email/Webhook通道配置项完整，实盘只需填入配置即可使用
