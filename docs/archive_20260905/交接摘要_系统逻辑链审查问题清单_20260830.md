## 二、问题清单（按严重度排序）

### 🔴 高严重度

#### #S1：事件发布链断裂——离线清洗场景下事件总线无发布者

| 项目 | 内容 |
|------|------|
| **问题描述** | 清洗流水线（`data_access/cleaner/` 全部6个文件）和数据管理器（`manager.py`）都没有发布任何事件到事件总线。`DataQualityEventPublisher` 只在 `event_bus.py` 的示例代码中被实例化，没有在实际业务代码中使用。 |
| **实际调用点** | 全项目 `publish_data_quality(` 实际调用点仅3个：<br>1. `core/event_bus.py:624` — 示例代码<br>2. `core/event_bus.py:1515` — `DataQualityEventPublisher` 内部方法<br>3. `live/data_feed.py:1755` — 实时数据流发布脏数据事件 |
| **影响** | `risk_manager.py` 订阅的 `DATA_QUALITY_ALERT`/`DATA_QUALITY_PIPELINE_COMPLETE`、`alerting.py` 订阅的 `DATA_QUALITY_DIRTY`/`DATA_QUALITY_ALERT`/`DATA_QUALITY_PIPELINE_COMPLETE`、`metrics_collector.py` 订阅的 `DATA_QUALITY_DIRTY`/`DATA_QUALITY_PIPELINE_COMPLETE`，在离线清洗场景下永远不会被触发。只有实时数据流（`live/data_feed.py`）会发布事件。 |
| **逻辑链断裂** | 事件总线设计为"清洗→风控/告警/指标"联动，但离线清洗时这条链完全断裂。`scripts/数据清洗.py` 运行清洗后，风控不会暂停、告警不会触发、指标不会采集。 |
| **修复方案** | 在 `data_access/cleaner/pipeline.py` 中集成 `DataQualityEventPublisher`：<br>1. `CleanPipeline.__init__` 添加 `event_bus`/`enable_events` 参数，初始化发布器<br>2. 新增 `_publish_dirty_event()`：标准清洗步骤后汇总发布脏数据事件<br>3. 新增 `_publish_pipeline_complete_event()`：流水线完成（成功/失败）时发布完成事件<br>4. 新增 `_publish_quality_alert_if_needed()`：按脏数据占比分级发布告警（≥50% critical / ≥10% error / ≥5% warning）<br>5. `run_clean_pipeline()` 旧版函数同步集成事件发布<br>6. 所有事件发布用 try-except 包裹，失败不影响清洗结果 |
| **修改文件** | `myquant/data_access/cleaner/pipeline.py` |
| **状态** | ✅ 已修复（2026-08-30） |
| **验证结果** | 导入测试通过；运行时测试验证：脏数据事件✅、流水线完成事件✅（含失败时status=failed）、质量告警✅（critical级正确触发）、事件发布失败不影响清洗结果✅ |

## 四、#S1 修复详细记录

### 修改文件
`myquant/data_access/cleaner/pipeline.py`

### 修改内容

#### 1. 新增导入（第53行）
```python
from myquant.core.event_bus import DataQualityEventPublisher
```

#### 2. CleanPipeline.__init__ 新增参数（第357-414行）
- 新增 `event_bus: Optional[Any] = None` 参数
- 新增 `enable_events: bool = True` 参数
- 初始化 `self._publisher: Optional[DataQualityEventPublisher] = None`
- `enable_events=True` 时尝试创建发布器，失败则记录警告并设为 None（不影响清洗）

#### 3. 新增三个事件发布方法（_update_stats 之后）
- `_publish_dirty_event()`：标准清洗步骤后汇总发布脏数据事件（统计错误类型分布，取主要类型+top5错误）
- `_publish_pipeline_complete_event(result)`：流水线完成（成功/失败）时发布完成事件（含cleaned/bad/total/bad_ratio/duration/steps/bad_file/report_file/error）
- `_publish_quality_alert_if_needed()`：按脏数据占比分级发布告警（≥50% critical / ≥10% error / ≥5% warning / <5% 不发布）

#### 4. _execute_pipeline 集成事件发布点
- 标准步骤（validate/deduplicate/detect_anomalies/sort）后调用 `_publish_dirty_event()`
- `_update_stats()` 后调用 `_publish_quality_alert_if_needed()`
- `on_pipeline_complete` 钩子后调用 `_publish_pipeline_complete_event(result)`
- except 块中也调用 `_publish_pipeline_complete_event(result)`（失败时 status=failed，确保下游感知）

#### 5. run_clean_pipeline 旧版函数同步集成
- 在 return 前创建独立 `DataQualityEventPublisher(source="run_clean_pipeline")`
- 依次发布：脏数据事件（如有）→ 质量告警（按比例分级）→ 流水线完成事件
- 全部 try-except 包裹，失败不影响清洗结果

### 设计原则
1. **事件发布可选**：`enable_events=False` 可完全关闭，不影响现有功能
2. **失败隔离**：所有事件发布用 try-except 包裹，事件总线故障不影响清洗流程
3. **性能友好**：脏数据事件汇总发布（不逐条），避免高频事件压垮事件总线
4. **实盘无缝对接**：与 `live/data_feed.py` 使用同一套事件类型和发布器，离线/实时统一
5. **向后兼容**：`run_clean_pipeline()` 函数签名和返回值不变，现有调用方无需修改

### 验证结果
- ✅ 导入测试：CleanPipeline/run_clean_pipeline/PipelineResult 全部导入成功
- ✅ 属性检查：`_enable_events`/`_publisher`/三个事件发布方法均存在
- ✅ 禁用事件：`enable_events=False` 时 `_publisher=None`，不创建发布器
- ✅ 运行时测试（CleanPipeline）：脏数据事件发布✅、流水线完成事件发布✅（含失败时status=failed）
- ✅ 运行时测试（run_clean_pipeline）：脏数据事件✅、质量告警✅（critical级正确触发，脏数据占比100%）、流水线完成事件✅
- ✅ 失败隔离：事件发布异常不影响清洗结果返回
