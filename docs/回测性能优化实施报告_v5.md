## 一、项目概述

### 1.1 背景与问题

原系统为事件驱动回测架构，在面向大批量参数扫描与多标的批量回测时存在五类根因问题：

| 问题 | 表现 |
|---|---|
| 架构错配 | 事件驱动逐 bar 循环与"批量参数扫描"场景不匹配，计算密集场景吞吐不足 |
| 重复计算 | 因子/指标在多次回测间重复计算，无缓存复用 |
| I/O 阻塞 | 数据加载无预取/流水线，磁盘 I/O 阻塞计算 |
| GC 压力 | 事件对象大量创建销毁，垃圾回收成为隐性损耗 |
| 并行不合理 | 并行任务存在 L1 缓存失效、pickle 序列化失败、内存 OOM 等隐患 |

### 1.2 目标

1. **完整实现纯向量化引擎 `vectorized`**（面向大批量参数扫描，不阉割）；
2. **新增 `mixed` 混合引擎作为生产主力**（向量化因子 + bar 循环处理路径依赖/止损/条件单）；
3. **保留 `event` 事件驱动引擎作为真值基准**（上线前必须 event 模式全量验证一次）；
4. 修复原版工程缺陷：缓存失效风险、并行 L1 缓存失效、pickle 序列化风险、OOM 内存溢出、费用逻辑漂移、硬编码一致性阈值；
5. 配套缓存体系、数据指纹、内存防护、增量回测、完整测试与 CI 回归；
6. **实盘链路 `live/risk/execution` 保持零修改**，回测优化全部隔离在 `backtest` 模块，不影响实盘稳定性。

### 1.3 落地红线（团队共识）

1. **定位**：`vectorized` 用于大批量参数扫描；**`mixed` 为生产主力**；`event` 作为真值基准，上线前必须 event 模式做一次全量验证。
2. **CI 必须执行三模式一致性回归**，防止迭代带来逻辑漂移。
3. **并行任务 L1 命中率下降属于预期行为**，不可使用单进程热缓存指标验收多进程场景。
4. **数据更新流程必须**：更新数据指纹 + 主动缓存失效；回测异常优先排查缓存。
5. **实盘模块 `live/`、`risk/`、`execution/` 禁止修改**，回测优化全部隔离在 `backtest` 模块。

## 二、总体方案与架构

### 2.1 三模式引擎架构

```
                    ┌─────────────────────────────────────────────┐
                    │         BacktestScheduler（三模式调度）        │
                    │    auto 解析 → 按策略 engine_modes() 优先级     │
                    │          vectorized → mixed → event           │
                    └───────────────┬───────────────┬───────────────┘
                                    │               │
          ┌─────────────────────────┘               └───────────────┐
          ▼                                                   ▼
┌───────────────────┐                    ┌─────────────────────────────┐
│  VectorizedEngine  │                   │  MixedBacktestEngine         │
│  纯向量化（numpy）   │                   │  向量化因子 + bar 循环          │
│  大批量参数扫描      │                   │  处理路径依赖/止损/条件单        │
└───────────────────┘                    │  生产主力模式                  │
                                        └─────────────────────────────┘
                    ┌─────────────────────────────┐
                    │  BacktestEngine（event 保留） │
                    │  事件驱动，真值基准           │
                    └─────────────────────────────┘
                        ▲ 三引擎共用撮合/费用口径 ▲
        ┌───────────────┴──────────────┴───────────────┐
        ▼                                              ▼
   order_matcher.py（统一撮合）                 fee_common.py（唯一费用入口）
   T+1 / 滑点 / 部分成交 / 条件单                佣金/印花税/过户费/滑点统一口径
```

**统一口径设计**（消除漂移的关键）：
- `backtest/fee_common.py`：全局唯一费用计算入口，向量化 + 标量两套实现，彻底消除多引擎费用逻辑漂移；
- `backtest/order_matcher.py`：统一撮合底层，三套引擎共用同一套撮合逻辑（市价/限价/止损/条件单、T+1、滑点、部分成交）；
- `strategies/base.py`：策略基类扩展三套接口 `on_bar / generate_signals_vectorized / generate_mixed_loop`，未实现接口抛出明确提示异常。

## 六、局限与中长期演进路线

### 6.1 本次版本的已知局限（短期已做缓解）

| # | 局限 | 本次版本缓解 | 残留敞口 |
|---|---|---|---|

| L2 | 并行关闭 L1 后，L2 磁盘 I/O 成为瓶颈 | parquet 调优 + 预热脚本 | 多进程冷启动 I/O 竞争 |

| L4 | >1000 超大规模标的内存压力 | 内存水位监控 + 分块流水线降级 | 全量驻留内存场景仍受限 |
| L5 | 真实策略 mixed vs vectorized 存在约 0.3% 自然差异（策略两接口实现差异） | 一致性校验如实告警、按需放宽阈值 | 语义级差异需策略层对齐，非引擎层问题 |

| L8 | 性能基准结果未落盘持久化 | engine_benchmark 输出 summary + to_dict JSON 可序列化 | 尚无自动归档/趋势对比能力 |
| L9 | Redis / pika 等可选依赖未实际部署 | pyproject 已声明（cache/live 分组），延迟导入可降级 | 分布式能力需按需启用 |
| L10 | 业务策略尚未全量迁移三接口 | 六个示例策略双接口改造完成 | 业务策略迁移属独立迭代，不在本次优化范围 |

### 6.2 中长期演进路线（v2 规划）

**短期（v1.5，1-2 个迭代）**：
1. mixed 引擎循环内局部向量化 + numba 可选开关（L1）；
2. parquet 写调优 + 冷启动预热脚本（L2）；
