## 一、背景与目标

系统已具备较完整的风控组件（双层风控、熔断器、应急清仓、防未来函数门禁、仿真准入评估、账户对账），但经逐行核验发现：**保障组件大量没有装配进实盘进程**，导致"代码全在、装配为零"。

**核心判断（顾问结论）**：这个系统缺的不是风控逻辑，是把风控逻辑放进真钱进程的那根线。风险敞口主要由 L3（运行）与 L4（应急）两层决定，而这两层恰恰最薄。

本方案目标：

1. **让已有的保障组件在真钱进程里真正通电**（熔断、守护、看门狗、准入守卫、异常交易规则、broker 边界硬闸）；
2. 建立**全局 fail-closed 语义**，并区分"能力缺失"与"外部依赖不可用"两类失败；
3. **定义并守护应急链不变量**——安全门禁不得把刹车锁死；
4. 补齐**复位路径**（四问中的"复得了位"），避免"停了但没完全停 / 复位了但另一个还停着"；
5. 用**故障注入**证明"该拦的拦得住、不该拦的没拦、告警真能送达"；
6. **定义 LIVE 上线门槛**——没有额度闸与准入凭证，任何阶段都不允许真钱首启；
7. 接入项目既有治理纪律（蓝图优先 / 回写编号 / R-04 阈值真源）。

## 二、总体原则

| 原则 | 说明 |
|---|---|
| **不推倒、不新造** | 90% 的问题是"接线"不是"缺件"；第0阶段全部是装配 + 断言 + 启用已有规则 + 一处边界硬闸（0.9） |
| **fail-closed 是位置属性** | 门禁"不可绕过"取决于闸口所在层，而非模块是否存在 |
| **fail-closed 必须区分失败类型** | "能力缺失"→拒启；"外部依赖不可用"→降级 + CRITICAL；分类不确定默认拒启（§十.5） |
| **双层纵深** | 外层丰富规则（引擎层，可绕过也无妨）+ 内层不可绕过硬闸（broker 提交边界，0.9 落地） |
| **刹车优先于门锁** | 任何门禁改造不得削弱应急平仓能力（§三 不变量） |
| **有置位必有复位** | 新增任何"停止"能力，必须同时定义复位路径、复位权限与幂等性；**复位只清自己置位的** |
| **无额度闸不上线** | LIVE 首启必须过上线门槛（§八 第0阶段末尾） |
| **先让它能停 → 再看得见 → 最后拦得准** | 实施顺序；应急能力优先于监控能力 |
| **分级处置** | 自动阻断（禁开仓/撤单）→ 人工放行（不可逆动作须显式 confirm）→ 全部审计留痕 |
| **自动保护动作不纳入人审** | 准入守卫防的是误操作，不是防自动保护（§十.3） |

## 三、不变量清单（硬约束，任何施工不得违反）

> 施工红线，与功能需求同等优先级；每条配套反向验收用例（§九.2 / §九.3）。

- **I-1 应急链必须独立于所有门禁**：应急平仓链（`scripts/一键平仓.py` → `myquant/live/emergency_liquidation.py`）不得依赖 `create_live_engine` / `validate_live` / `ComplianceGate` / `OperationGuard` / `CircuitBreaker` 中的任何一个。依据：`scripts/一键平仓.py:28` 明确"脚本不加载策略/引擎/风控，崩溃场景也能独立运行"，此性质今天成立，是 L4 的命根子。
- **I-2 停止能力必须可复位，且复位权限明确**：任何置位 `PAUSED` / 熔断 / 引擎停止的机制，必须在 §七 语义矩阵登记：谁置位、谁有权复位、复位是否幂等、是否被状态查询观测。
- **I-3 只禁开仓，不禁退出**：所有"停止"语义一律**只约束 BUY / 新开仓**；撤单、卖出、平仓、应急路径必须始终可用。依据：本项目已两次在此栽过——P1-01（累计下单上限导致止损卖单被拒、持仓无法退出）、P1-18（黑名单禁止卖出导致困仓）。
- **I-4 自动保护动作不要求人工复核**：`force_close` 等由系统发起的保护动作不得因 `require_reviewer` 被拒绝（见 §十.3）。
- **I-5 阈值不得自行编造**：所有阈值/时限引用既有真源（`config/settings.yaml` 的 `monitoring.slo.*`、`docs/监控档案/SLO与阈值锁定清单_P0-2.md`、`docs/监控档案/可测量性与故障注入规范_P0-8.md` 的 MTTx 口径），不硬编码第二套数值（R-04）。
- **I-6 新增文件必须先登记蓝图**：按项目治理纪律，新建文件须先登记 `docs/project_layout_gear2.md` 目录树并占用回写编号（见 §十一）。
- **I-7 未过上线门槛不得 LIVE 首启**：LIVE 首启条件见 §八 第0阶段末尾；任何阶段、任何绕过方式都不得在门槛未过时上真钱。

## 四、分层模型（决策时点 + 四问验收）

按"资金离场前的决策时点"分五层，每层用四问验收：**到得了、拦得住、看得见、复得了位**。

| 层 | 时点 | 现有承载 | 失效后果 |
|---|---|---|---|
| L0 准入 | 人、进程外 | `validate_live` / `ComplianceGate` / 平台校验 / **券商侧限额** / **LIVE 上线门槛** | 拿错账户、没备案就上真钱 |
| L1 装配 | 进程内一次 | `check_mode_consistency` / `leakage_gate` / `state_store` 必填 / **启动自检断言** | 配置漂移，风控被静默跳过 |
| L2 订单 | 每单、提交前 | `RiskManager.check_order`（14 规则中实际启用 11 条，见缺口11）+ fail-closed + 幂等 + `LookaheadGuard` + **broker 边界硬闸（0.9）** | 单笔错误直接真钱成交 |
| L3 运行 | 周期/事件 | Guardian 巡检、熔断、对账、看门狗 | 持续错误累计成大亏 |
| L4 应急 | 事后 | `EmergencyLiquidationService`、Kill Switch、人工 SOP、**独立监护进程（规划）** | 停不下来、退不出去 |

> **核心判据**：L2 决定"单次错误多贵"，L3 决定"错误能持续多久"，L4 决定"你还有没有救"。
> **四问覆盖要求**：每一层都必须能回答四问；任一问无对应施工项，视为该层未完成。优化版的「复得了位」在 L3 已由 §七 + §八（0.2）+ §十.4 补齐；V3 追加"告警送达"为"看得见"的硬验收（§九.1 用例12）。

## 七、暂停/复位语义矩阵（对应不变量 I-2）

> 施工前必须先把本表填满；未登记的"停止"能力不得进入施工。

| 停止机制 | 置位者 | 复位者 | 复位幂等 | 复位是否清除其他暂停 | 引擎可观测 | 当前覆盖 |
|---|---|---|---|---|---|---|
| `RiskManager` 手动 `pause()` | 人 / API | `resume()` | 是 | **是（会清数据质量暂停）** ⚠️ 见 A1 | 经 `/api/risk/status`（当前伪状态） | 部分 |
| 熔断 `pause_for_circuit_breaker()` | `CircuitBreaker` | `resume_from_circuit_breaker()` | 是 | **否（只回滚自己）** ✅ 正确 | 否 | ❌ 未装配 |
| 数据质量暂停（全局/单标的） | 事件总线 | `resume()` / 自动恢复 | 是 | 是 | 部分 | ✅ |
| `engine.pause()` | 巡检 / 人 | `engine.resume()` | 是 | **须隔离（不得经 `resume()` 误清数据质量暂停）** | 否 | ❌ 未通电 |
| `ActionEngine` Kill Switch | 人（需新增端点） | `set_kill_switch(False)` | 是 | 否 | 经 action_engine 状态 | ⚠️ 无端点 |
| `monitor_only` | 启动参数 | 重启 | — | — | 是 | ✅ |

> **A1 硬约束（V3）**：`engine.pause()`/`resume()` 与 `RiskManager` 的同步置位/复位，**禁止直接调用 `risk_manager.resume()`**（已核验 `risk_manager.py:740-746`：`resume()` 会清除所有数据质量暂停标记）。必须仿照 `_circuit_paused` 先例（`risk_manager.py:826`）增加隔离的暂停标志与复位方法，复位只清自己置位的。

**两个必须消除的坏场景**：

- **场景1「复位了但系统已死」**：巡检 CRITICAL → `engine.pause()` → 引擎不再产生信号。人事后经 API 复位熔断 → `risk_manager.resume()` → **引擎仍 PAUSED、静默停摆**，而风控状态显示 NORMAL。
- **场景2「告警噪音淹没真信号」**：熔断置 risk PAUSED，引擎仍 RUNNING → 继续生成信号 → 每单被 `_risk_manager_check` 拒 → `engine.py:1737` `guardian.record_rejection()` 累加 → 达阈值触发 guardian 的 PAUSE 决策 → 每 60s 一条 CRITICAL 告警。

**处置**：见 §八 第0阶段 0.2（`engine.pause` 同步置风控，复位用隔离语义）与 §十.4（决策点4：暂停语义权威源）。

## 十、需拍板的决策点

### 10.1 决策点 1：Kill Switch 的语义

**推荐：`禁开仓 + 撤全部挂单`，全平必须人工二次确认（保持 `auto_liquidate=False`）。**

**理由（用不可恢复性论证，而非"损失多大"）**：需要监护进程介入的场景，本身就是**主通道不可靠**的场景（断连 / 僵死 / 对账失败）。此时自动全平依赖的正是那条不可靠通道——委托可能全部失败、部分成交、或严重滑点，产生一个**更难恢复的中间状态**（部分平仓 + 未知成交 + 账实不一致）。**不可恢复性——而不是"多持有几小时"——才是拒绝自动全平的理由。** 全平保留为"人工 + 可靠通道恢复后"的动作。

> 附注：日线 + A股 T+1，当日买入不可卖，盘中强平只能卖存量老仓；连续跌停 / 流动性枯竭时"多持有几小时"等于多个跌停板。结论不变，但不可恢复性是更硬的论据，且直接支撑不变量 I-1。

**配套硬约束**：阶段4 独立监护进程必须遵循同一语义——**只 `cancel_all` + 禁开仓，不自动全平**。

### 10.2 决策点 2：跨进程急停

**推荐：`文件信号 + 独立监护进程读`，且与阶段4 合并成一条通道；必须带 ack 回路。**

理由：同进程起 API 会把"监控面崩 → 交易面崩"耦合；文件信号零依赖、进程崩了文件还在、可审计；阶段4 本来就加独立监护进程，由它消费急停信号——**API 只负责"写急停标志"，监护进程负责"cancel_all + 禁开仓"**，职责彻底解耦。

**ack 回路（必做，否则制造假的"已急停"）**：

1. 写入标志时记 `requested_at` + 请求方；
2. 监护进程消费后写 `ack` 文件（含 `acted_at` + 动作结果）；
3. API / 看板读 ack，**超时未 ack → 升级 CRITICAL，并明确提示"急停未生效，请用一键平仓"**。

> **为什么必须有 ack**：监护进程可能没在跑（未启动、崩了、被误杀）。此时人写了标志、界面显示"已急停"，而交易进程照旧开仓——**这比没有急停更危险**，因为人不再采取其他手段。

### 10.3 决策点 3：单人系统的"复核"替代物

**推荐：`冷却期 + 二次令牌`，绑定两个约束，并解决 actor_type 语义冲突。**

没有第二个人，双人复核是空话。用**时间成本**换掉**第二双眼睛**：

- LIVE 切换与熔断复位都要求"申请 → 等待 N 分钟 → 用带过期时间的令牌确认"；申请与确认都进不可篡改审计（`audit_log.py` 只追加三表）。
- **绑定①**：令牌绑定 `effective_config_digest`（与 §八 第3阶段准入凭证合并），配置一变令牌即失效；
- **绑定②**：令牌带 TTL（如 15 分钟过期），申请到确认的时间窗本身构成冷却期。

**必须同时解决的语义冲突**：`OperationGuard` 现要求 `reviewer` 字符串（`auth.py:299` 注释即"职责分离第二人"）。若直接启用 `require_reviewer`：`run_mode` 的 LIVE 切换调用（`run_mode.py:170`）不传 reviewer → 被拒（符合本意）；但 **`guardian.force_close_*`（`guardian.py:536/595`）也不传 reviewer → 同样被拒，即"应急强平被准入守卫焊死"。**

**推荐改法（首选第一个）**：`check()` 增 `actor_type: "human"|"system"`。`force_close` 由 system 发起时走**单向安全**判定（只要求属于可信自动处置链，不要求 reviewer）；人为发起的 `mode_switch_live` / `reset_circuit_breaker` 才要求复核人/令牌。**准入守卫防的是误操作，不是防自动保护动作；把自动保护动作也纳入人审，等于取消保护。**

> **实施顺序约束**：本决策点未定，**0.4 不得开工**（§八 第0阶段已注明）。

### 10.4 决策点 4：暂停语义的权威源是谁？

**推荐：以风控状态为权威，引擎状态为其投影。**

- 判定式：`允许开仓 = (risk 未 PAUSED) AND (engine 非 PAUSED) AND (circuit 未 tripped)`；
- `engine.pause()` 必须**同时**置风控暂停（或引入统一的 stop coordinator，把 §七 矩阵收敛为单点）；
- 复位时同理：一次复位动作应同步清除所有由它置位的标志，且**只清自己置位的**（沿用 `_circuit_paused` 先例 `risk_manager.py:826`）。**A1 硬约束**：引擎与风控的同步复位**禁止直接调 `risk_manager.resume()`**（会清数据质量暂停，`risk_manager.py:740` 已核验），必须新增隔离的暂停标志与复位方法；
- `/api/risk/status` 必须同时暴露三个状态与"当前是否允许开仓"的计算结果。

依据：§七 的两个坏场景。

### 10.5 决策点 5：门禁失败时"拒启"还是"降级运行"？

**推荐：按失败类型二分，不得一律拒启。V3 补分类判定标准（A3）。**

| 失败类型 | 示例 | 处置 |
|---|---|---|
| **能力缺失**（本系统自身装配问题） | 熔断未注入 / guard 未注册 / `pause_on_critical` 未生效 / 风控库为空 | **拒启**（正是 0.8 要的） |
| **外部依赖不可用**（本系统之外） | 事件总线偶发不可用 / NTP 不可达 / 券商 SDK 未连 | **降级 + CRITICAL，不拒启** |

**分类判定原则（A3，V3 新增）**：
- 以**"是否本系统代码/装配问题"**为第一判据：装配缺失、规则库为空、依赖未注入 → 能力缺失（拒启）；
- 外部服务/资源偶发不可用（总线抖动、NTP 不可达、券商网络）→ 外部依赖（降级）；
- **分类不确定时默认 fail-closed（拒启）**——宁可启动被拒，不可带病上线；
- 边界示例（写死，防施工争议）："事件总线不可用导致熔断事件收不到"按 **能力缺失** 处置（后果等同熔断未装配），不能按外部依赖降级放行。

> **为什么必须区分**：一律拒启会让"事件总线抖动一次"等于"无法启动一个正需要平仓的系统"。而应急链（I-1）虽独立，但正常交易能力被不必要地剥夺同样是风险。
> 同时统一 `auth.py:332` 的 fail-safe（配置装载失败→放行）与 0.4 的 fail-closed（未装配→拒绝）语义：**建议保留 `auth.py` 的 fail-safe 并显式声明"误配置不阻断"，避免施工者按 0.4 一并改掉，导致配置一坏连应急链都进不去。**
