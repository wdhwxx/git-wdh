# 量化系统监控模块施工总清单（V1.2）

**版本**：V1.2（正式修订版）
**上一版**：V1.1
**修订说明**：在 V1.1 骨架（优先级排序、A/B/C/D 四包、自动化三阶段安全模型）不动的前提下，补齐 V1.1 分析评估发现的两类系统性短板——**① 验收指标的可测量定义**（误报/准确率 ground-truth 判定、MTTx 计时起止点、标准故障注入用例集），**② 单人资源与工程量的匹配**（引入 M1-Min 保底交付子集）；并对事件驱动 vs 周期巡检边界、数值阈值锁定、可选项启用决策、监控面自身安全做增量补强。对应修订项 R-01~R-08。
**依据**：《量化系统监控模块可行性维护实施报告》V1.0（下文简称"报告"）＋《施工总清单 V1.1》分析评估报告 ＋ V1.2 修订清单

**优先级**：交易连续性 > 资金安全 > 风控不击穿 > 对账一致 > Alpha 有效 > 智能自治（报告 §0）

> **里程碑拆分说明（R-03）**：M1 拆为 **M1-Min（保底保命闭环）** 与 **M1-Full（完整保命层）**。单人资源受限时先交付 M1-Min，验收通过即视为"保命闭环达成、可对外交付一个安全下限版本"，再滚动扩展 M1-Full。裁剪边界与触发规则见 §11。

**核心原则（报告 §1.3 + 评估审议，全部施工项必须遵守）**：
1. 业务优先——技术指标服务于交易、风控、资金、Alpha；
2. 非侵入——采集异步、旁路，严禁阻塞交易热路径；
3. 流批一体——实时告警用事件流，T+1 归因/对账用批任务；**硬约束（R-02）：凡 KPI-2 要求 MTTD<1min 的 P0 故障，其检测必须由事件流实时触发（订阅 EventBus），周期巡检（默认 60s）仅作漏检兜底，二者不可互相替代；周期落库（BASE-2）不得作为任何 P0 实时告警的检测来源。**
4. 告警可行动——每条 P0/P1 告警必须绑定 Runbook 和责任人；
5. 监控自身高可用——单机语境下定义为：冗余通道 + 落盘兜底 + 外部独立告警（KPI-8 重定义）；
6. 版本贯穿——策略、模型、数据、配置、代码版本可追踪；
7. 监控即代码——仪表盘、告警规则、Runbook 均版本化；
8. **自动化安全先行**——所有自动动作先 shadow 只读，再人工确认，最后逐步放开；Kill Switch 独立于规则引擎。
9. **阈值单一真源（R-04）**——所有 SLI/SLO 数值阈值在 P0-2 一次性锁定，各包实现只引用 `monitoring.slo` 配置块，禁止在各自代码/文档内自定义阈值。
10. **验收可复现（R-01/R-07）**——所有验收指标按 P0-8 定义的口径自动统计，MTTx 一律以系统时间戳计算，禁止人工估算/人工计时。

### P0-8 展开（可测量性与故障注入规范）

**① 误报 / 准确率判定规则（ground-truth 定义）**
- **真告警（TP）**：告警产生后在 Runbook 中被确认（acked）为"需处置"，或在 resolved 时标记根因为真实系统/市场事件。
- **误报（FP）**：告警产生后被人工标记为"误报/噪声/已自愈无需动作"，或在无处置动作下自动 resolved 且元监控确认无对应真实事件。
- **漏报（FN）**：由 P0-8③ 故障注入用例集主动测量——注入的故障未被任何告警捕获即计为漏报。
- **统计口径**：`准确率 = TP/(TP+FP)`，`误报率 = FP/(TP+FP)`，`检出率 = TP/(TP+FN)`；数据源为告警表（BASE-1）的 `status` + 新增 `classification`（TP/FP/自动）字段，由 §7 周复盘任务**自动统计**，人工仅在周复盘对自动分类结果抽检校正（抽检比例 ≥ 20%）。

**② MTTx 计时起点 / 终点定义（一律以系统时间戳计算，禁止人工估算）**
- **MTTD（检测）**：起点 = 故障注入脚本写入的"故障发生时间戳"（事件时间，非告警时间）；终点 = 对应告警在 BASE-1 落库的 `created_at`。
- **MTTA（确认）**：起点 = 告警 `created_at`；终点 = 告警 `acked_at`（以系统确认事件为准，不以"人看到"为起点）。
- **MTTR（恢复）**：起点 = 故障注入时间戳；终点 = BASE-1"告警→恢复"成对记录中的 `resolved_at`（健康恢复自动发 INFO 并置 resolved）。

**③ 标准故障注入用例集（FI，与 D-6 混沌工程共用同一用例库）**

| 用例 ID | 注入故障 | 期望捕获项 | 触发模式 | 期望告警级别 | 对应 KPI |
|---|---|---|---|---|---|
| FI-01 | 行情源断流（交易时段停喂 bar） | A-4 StalenessDetector | EVENT | P0 | MTTD<1min |
| FI-02 | 引擎僵死（get_status 无响应） | A-5 引擎心跳 | POLL（窗口<60s） | P0 | MTTD<1min |
| FI-03 | 券商连接断开 | A-6 _check_broker | EVENT | P0 | MTTD<1min |
| FI-04 | 伪造拒单 | A-8 ORDER_REJECTED | EVENT | ERROR/P1 | MTTA<5min |
| FI-05 | 人为制造持仓差异 | A-7 reconcile 差异 | EVENT | CRITICAL | MTTR<30min |
| FI-06 | 告警主通道故障 | A-9 冗余/落盘兜底 | 元监控 | 元监控 | KPI-8 |
| FI-07 | 主进程 kill | BASE-8 外部心跳超时 | 外部通道 | 外部通道 | KPI-8 |

FI 用例集为 §9 KPI-2 计时与 KPI-3 检出率的唯一权威来源；每次演练逐用例跑、逐用例计时、结果入库。

## 11. 实施顺序（滚动交付 M1–M4，M1 拆 Min/Full · R-03）

- **前置规范**：P0-1~P0-8（含 P0-7 安全合规、P0-2 阈值锁定、P0-8 可测量性与故障注入规范）
- **公共底座**：BASE-1/3（保底）先行；BASE-2/4/5/6/7/8/9 随 M1-Full 补齐
- **M1 保命·Min（保底交付集，先交安全下限版本）**：P0-1/2/3/4 + BASE-1/3 + A-3/A-4/A-6/A-7/A-8/A-9 → 验收 A-15-Min，达成"保命闭环"
  - 为何是保底：P0 地基（文档为主、成本低）；BASE-1/3 是保命闭环的数据与配置底座；A-3 是 EVENT 类检测的前提（无事件流则 R-02 全落空）；A-4 行情活性是交易连续性第一杀手；A-6 券商断连=P0 交易中断；A-7 资金安全底线；A-8 拒单/成交失败闭环；A-9 保命告警必须可达（KPI-8）
- **M1 保命·Full（资源恢复后扩展层）**：M1-Min + {BASE-2/4/5/6/7/8/9, P0-5/6/7/8, A-1/2/5/10/11/12/13/16, A-14（按矩阵）} → 验收 A-15-Full
- **M2 保钱·核心**：B-1（实时对账）/B-3（限额）/B-6（熔断）/B-9（保证金）/B-7（数据新鲜度） → Phase 2 核心
- **M3 保Alpha·精选**：C-1（漂移实时化）/C-2（滚动绩效）/C-6（动态基线）/C-10（回测一致性） → Phase 3 精选
- **M4 自治·只读先行**：D-1 三阶段逐步放开（shadow 只读建议 → 人工确认 → 自动执行），D-2 自愈动作先 shadow 演练 → Phase 4

**触发规则（R-03）**：若 M1-Min 未达验收即开始 M1-Full，视为违规排期；M1-Min 验收通过即视为"保命闭环达成"，可对外交付一个安全下限版本。

每个里程碑完成即跑本包验收 + 现有 `pytest tests/unit/` 监控相关用例，确保零回归；验收准确率类指标按 P0-8 口径自动统计、按周统计至少 4 周；涉阈值项核对配置与 P0-2 锁定表一致。

**资源约束与关键人**：单人 + 现有组件（EventBus / RabbitMQ / SQLite / AlertManager / scheduler），不引入 Kafka/Flink/ClickHouse/Temporal 等重型中间件（报告 §2.1 技术栈按单机规模择优替换）；全量施工项约 60+，单人多角色下 M1 全量极可能翻倍，**故设 M1-Min 保底交付集，把资源缺口变成显性裁剪边界**；**建议至少两人熟悉监控系统，避免知识单点**。
