## 1. 背景与目标

### 1.1 为什么现在做

项目已建成相当完整的门禁体系：`tests/unit/test_architecture.py` 单文件 1,125 行、30+ 条规则，锁定架构违规数、真环数、超大文件行数、入口白名单、脚本类定义、事件契约、配置死键、**零覆盖模块引用级快照**；CI 配置侧还有 `RUFF_BASELINE`、`BLE001_BASELINE` 两道 lint 棘轮（**v1.2 注：配置存在，但从未接线执行，见 §2.6 / G-7**）。这是一套以「基线锁定 + 只减不增 + 新增即红」为核心的成熟范式。

但这套体系里**唯独没有一条门禁管「测试到底执行了多少代码」**：

- 全库检索 `--cov` / `fail-under` / 覆盖率门禁，仅在两份架构治理文档里留下一句自述：**「CI 无 cov/fail-under」**（`鲲鹏量化交易系统_架构分层治理方案_v5.3.md:183`）。无任何实现。
- `R-20` 锁的是**测试函数的数量**（`count >= 3310`，当前实测 3,750，余量 440）——一个断言为空的测试同样满足它。
- `R-19` 锁的是**引用级零覆盖**（"被 tests import 即视为覆盖"，AST 近似）。项目自己在 docstring 里诚实标注了这是近似口径，真实覆盖须由 pytest-cov 判定。

也就是说：**当前对"代码是否被真正执行过"这件事，项目没有任何可阻断的度量。**

### 1.2 目标

1. 建立**执行级**（pytest-cov 插桩，非引用级近似）覆盖率度量与阻断门禁。
2. 门禁必须**确定性可复现**——不随机器负载、时钟、网络漂移。
3. 门禁必须**进入 CI 并在 PR 上阻断**，且**不增加**（理想情况下降低）CI 总耗时。
4. 门禁判据与项目既有的「棘轮」范式同构，不引入第二套治理语言。
5. 覆盖数字**可解释、可归因**——能回答"哪个高风险模块缺覆盖"。

### 1.3 明确不做的事

- 不追求一次性把覆盖率拉到某个漂亮数字；只做**棘轮 + 分层下限 + 新增门槛**。
- 不把计时/性能基准纳入阻断门禁（见 §3 G-3）。
- 不以覆盖率替代行为正确性（见 §3 G-5）。
- 本报告**只出方案，不改动任何代码、配置、CI 与测试**。

>
> 其中 `architecture-gate` job 是**100% 冗余**——`test_architecture.py` 是 `tests/unit` 的子集，
> `test` job 已经完整跑过它。
>
> **结论比 v1.0 更强**：把冗余 job 去重腾出来的时间，**足够把覆盖率插桩装进去还净赚**。
> 覆盖率门禁不是"额外增加 CI 负担"，而是一次**净减负**的机会。
>
> ⚠️ **v1.2 前提修正**：以上全部是**对 `ci.yml` 文本的静态分析**，收益与耗时**只有在 CI 接线后才兑现**。
> 接线（P0-0）之前，这些 job 的实占耗时是 **0 分钟**，去重"省下"的时间同样不存在——所以本节的净减负结论**有效，但尚未生效**。

### 2.6 既有门禁资产盘点（按**实测效力**登记）

> ⚠️ **v1.2 修正**：本表 v1.1 版隐含一个**未经核验的前提**——"这些资产有个调度者在跑它们"。
> 经查（`.git/config` + 全树检索）：`origin` 是 Gitee，而 Gitee 不执行 `.github/workflows/`，`.workflows/` 亦不存在。
> 因此**凡列在 `ci.yml` 里的门禁，远程执行次数 = 0**。v1.2 新增"是否在运行"一列，把该状态显式暴露出来。

| 资产 | 位置 | 是否在运行（v1.2 新增） | 实测效力 |
|---|---|---|---|

## 5. 总体设计

### 5.1 门禁分层模型（按**风险**分层，不按架构层）

架构层（L0–L6）回答"依赖方向"，不回答"出错的代价"。门禁按资金安全代价分层：

| 层级 | 范围 | 覆盖下限（建议） | 阻断 |
|---|---|---|---|
| **T0 阻断级** | `leakage_gate/`、`realism_gate/`、`risk/`、`execution/`、`live/`、`engine/`、`backtest/{engine,mixed_engine,vectorized_engine}.py`、`strategies/kunpeng_strategy.py` | 总量 ≥ **68%** | ✅ 硬阻断 |
| **T1 严格级** | `core/`、`data_access/`、`database/`（**不含 migrations**）、`monitoring/`、`models/`、`indicators/`、`allocation/`、`ml/`、`strategies/`、`backtest/`（其余） | 总量 ≥ **60%** | ✅ 硬阻断 |
| **T2 常规级** | `api/`、`web/`、`gui/`、`utils/`、`acceptance/` | 总量 ≥ **52%** | ✅ 硬阻断 |
| **T3 报告级** | `database/migrations/`、`*_selftest.py`、性能基准 | 仅报告 + **迁移冒烟门禁**（§6.2 P1-7） | 覆盖率不阻断；冒烟阻断 |

> 阈值取"实测值 − 3~4pp"作为余量（T0 71.2→68、T1 62.9→60、T2 55.3→52）。
> 余量用于吸收**合理的**测试重构，同时"只增不减"由总棘轮兜底。

### 5.2 门禁判据

| # | 判据 | 形式 | 说明 |
|---|---|---|---|
| **C-1a** | **总量棘轮·绝对行** | `已覆盖行 >= COVERED_LINES_BASELINE` | **v1.1 新增**：防"删测试"（删掉已覆盖的测试→行数下降即红） |
| **C-1b** | **总量棘轮·百分比** | `覆盖率 >= COVERAGE_BASELINE` | 防"堆未测代码" |
| **C-2** | **分层下限** | `T0 >= 68%` / `T1 >= 60%` / `T2 >= 52%` | 防"外围刷量、红线烂内核" |
| **C-3** | **关键文件覆盖率下限** | 对 §5.2 表中 ~20 个具名文件设 floor，只增不减 | 兜住单文件级退化 |
| **C-4** | **新增文件门槛** | 新增 `myquant/**.py` 在 T0/T1 须 ≥ 60%、T2 须 ≥ 30%，否则红 | 「新增即红」，与 R-14/R-19/R-23 同构 |
| **C-5** | **存量文件语句数棘轮** | 每个 T0/T1 文件语句数只增不减（或设增长率上限） | **v1.1 新增**：封堵 G-11"把新代码塞进旧文件绕开 C-4" |
| **C-6** | **仅源码断言守护的模块数** | ≤ **4**，只减不增 | **v1.1 新增**：替代不成立的 `--cov-omit` 方案，保持 G-5 缺口可见 |
| **C-7** | **运行时跳过预算** | `pytest.skip` 实际触发数 ≤ **4**，只减不增 | 防 G-4 fail-open 回潮（见 §6.3） |

> **为什么 C-1a 与 C-1b 必须成对**：分层下限与百分比都是**比率**。
> 只靠比率时，"删掉 3,000 行**已被覆盖**的代码"会让比率不变甚至上升，**没有任何门禁报警**。
> 绝对覆盖行数是唯一能挡住这类的判据；反之，百分比是唯一能挡住"猛加未测代码"的判据。**缺一不可。**

### 5.3 基线棘轮机制

沿用项目既有做法，基线以常量形式冻结在门禁模块内：

```python
# 门禁核心集口径。全部数值须由 CI（Python 3.12）生成，不得手抄本地 3.11 数字。
COVERAGE_BASELINE: float = 62.0          # v1 学习期额度；CI 实测后替换
COVERED_LINES_BASELINE: int = 38300      # 绝对覆盖行数（CI 口径）
TIER_FLOOR = {"T0": 68.0, "T1": 60.0, "T2": 52.0}
FILE_FLOOR: dict[str, float] = { ... }   # 只增不减
FILE_STMT_CEILING: dict[str, int] = { ... }  # C-5
NEW_FILE_FLOOR = {"T0": 60.0, "T1": 60.0, "T2": 30.0}
SOURCE_ASSERT_ONLY_MAX: int = 4          # C-6
SKIP_BUDGET: int = 4                     # C-7
```

**余量取值（v1.1 修订）**

| 版本 | 建议值 | 依据 |
|---|---|---|
| v1.0 | 62.9（余量 **0.09pp ≈ 55 行**） | ❌ **过紧**：未说明理由，且不足以吸收一次正常测试重构 |
| **v1.1** | **62.0（余量 ≈ 1pp ≈ 600 行）** | 显式标注为**"学习期额度"**，承诺 1–2 个季度后收紧至接近零 |

> **为什么余量是"政策额度"而非"抗抖动缓冲"**：覆盖率在本项目是**确定性指标**（两次独立运行语句数完全一致）。
> 余量不为噪声服务，只为**合法重构**服务——这是两件不同的事，需要不同的尺子。

**基线治理规则（v1.1 新增，针对 G-7 的根因）**

`RUFF_BASELINE` 烂掉的根因**不是余量留少了，而是两年没人回去校准**。因此覆盖门禁必须自带：

1. **改基线须独立 commit + 写明理由**（禁止与业务改动混在同一提交里）；
2. **每季度必须至少上调一次**，否则门禁输出告警（防止棘轮单向松动）；
3. 基线常量的历史取值在 docstring 里留变更记录（同 `test_architecture.py` 的做法）。

### 5.4 覆盖率口径契约（必须先定死，否则数字会被反复误用）

| 契约项 | 规定 |
|---|---|
| 采集口径 | `pytest-cov`，`--cov=myquant` |
| **覆盖集** | `tests/unit` + `tests/leakage_gate` + `tests/realism_gate` + `tests/scripts`；**排除 `tests/benchmarks`** |
| **权威平台** | **单一**：CI 矩阵中的 **ubuntu-latest / Python 3.12** 腿。Windows 腿只跑测试不产覆盖率（平台条件分支会使两边数字不同，不指定即等于没定义基线） |
| 阻断主口径 | **行覆盖**（`num_statements` / `missing_lines`） |
| 分支覆盖 | **仅报告**，不入阻断 |
| 与 R-19 的关系 | **不混用**。R-19 为引用级近似（继续保留为廉价快照）；本门禁为执行级。两者数字**禁止相互引用** |

#### 6.1.1 `RUFF_BASELINE` 重基：三个方案与推荐组合

**共同前提**：CI 的 `lint` 逻辑是"数出违规数 N，若 `N > RUFF_BASELINE` 则失败"。重基 = 改这个常量。

> ⚠️ **v1.2 前提修正**：这段逻辑**目前没有任何执行者**（见 §2.6 / G-7）。因此下面三个方案**全部是"接线后"的取舍**；
> 接线前重基**不会让任何东西变绿**，只会把本机数字写成"官方基线"，属纯负收益动作（P0-2 已上封条）。
> 接线后的推荐顺序也随之变化：**方案 C（只扫 PR 变更文件）由"治本但麻烦"升为首推**——
> 它让 922 项历史债彻底退出议题，而 A/B 都得先把 922 消化成一个常量。

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 一次性重基 + `ruff --fix`** | 先自动修 750 项，再数剩下的，把基线设成剩余值（≈172） | 债真正减少 | diff 极大（跨 442 个 `myquant/`、330 个 `tests/`、126 个 `scripts/`、32 个 `run_*` 文件）；**"可自动修"≠"安全"** |
| **B. 纯重基** | 560 → 922，代码不动 | 10 分钟恢复保护（**v1.2：仅接线后成立**；接线前无"保护"可恢复） | 922 项债（含 45 项 F821）被**永久固化** |
| **C. 只扫 PR 变更文件** | 用 `git diff --name-only origin/main...HEAD` 拿文件清单喂给 ruff | **治本**，历史债退出议题 | 要改 CI 逻辑；需决定粒度（文件级 vs 变更行级）；PR/push 事件要分别处理 |

**`ruff --fix` 的真实风险（本次实测，含两处对早期判断的修正）**

✅ **先排除两个原本担心、实测证明不存在的风险**：

1. **"导入即注册"的 F401 不会被误删**。项目大量使用 `import myquant.x  # noqa: F401 导入即注册` 模式（如 `myquant/backtest/engine.py:124`、`myquant/leakage_gate/__init__.py:24-30`、`tests/unit/test_checks_causality.py:29`）。实测这些 noqa **全部生效**，**未出现在 922 项里**，`--fix` 不会碰它们。
2. **noqa 机制整体是好的，不是坏的**。实测 334 行带 `# noqa: BLE001` 的指令中，**仅 4 条失效**（≈98.8% 有效）。所以 922 项**不是**"抑制机制失灵造成的伪债"，而是**真实、机械式、可清理的债**。

⚠️ **真实存在的风险（保留）**：

| 风险 | 实例 | 为什么危险 |
|---|---|---|
| **重导出被当作"未使用导入"删除** | `myquant/backtest/engine.py:48-51` 的 `register_broker_factory` 被报 `F401 [*]`，但它是**注释写明、且有测试锁定**的故意重导出；**6 个生产入口**从 `engine` 导入它（`run_回测入口.py:340`、`baseline_archive.py:481`、`batch_backtest.py:48`、`param_optimizer.py:40`、`scripts/生成回测报告.py:216`、`scripts/验收_回测引擎V5.py:39`） | 删除即 **ImportError，回测起不来**。`tests/unit/test_assembly.py:99` 的重导出测试**会拦住**——但这是运气，不是设计 |
| **`E402` 在 `scripts/` 被"修复"** | 48 项 E402。`scripts/` 是**故意**的薄入口模式：必须先 `sys.path.insert` 再 `from myquant... import`。少数脚本的 `# noqa: E402` 写法无效（见下） | 把 import 提到顶部 → `myquant` 尚未进 `sys.path` → **ImportError** |

**根因**：ruff 的 F401 安全判定是**文件局部**的——它只看"本文件用没用"，看不到"别的文件从这里导入"。故 `[*]` 只能当参考。

**推荐组合（顺序不可颠倒）**：

> ⛔ **v1.2 封条**：整条链**在 P0-0（接线）完成前不得启动**——下面第 1 步"让流水线转绿"在没有流水线时无对象，
> 第 2 步会把本机 3.11 的数字固化成"官方基线"（§6.1 P0-2 已暂停）。

1. **先做 B**（10 分钟）让流水线转绿，恢复保护；
2. **再做 A，但分规则分批、每批跑全量测试**：
   - 第一批（零语义风险）：`I001` 导入排序 259 + `F541` 空 f-string 126 = **385 项**
   - 第二批（**必须先跑全量 pytest**）：`F401` 365 + `F841` 47 —— 重导出陷阱在此批
   - `E402` 48 单独处理，**只修 `myquant/` 内的，`scripts/` 内的人工确认**（薄入口纪律）
   - 清完再重基一次，压到 ≈172
3. **终态做 C**，让历史债彻底退出议题。

#### 6.1.2 `F821`（45 项）与 `# noqa` 格式缺陷

**F821 定性（v1.1 修正）**：45 项**绝大多数是未导入的类型名**用在注解里（`Optional`、`Any`、`Dict`、`Callable`、`List`、`Iterable`、`Tuple`），例如
`myquant/api/routes.py:161` 的 `def _mask_alert_details(details: Optional[Dict[str, Any]]) -> Dict[str, Any]:`。

- `myquant/` 中 **200/254** 个文件启用了 `from __future__ import annotations`（PEP 563，`routes.py:53` 即为其中之一）→ **注解不求值，运行时无害**。
- ⚠️ **但它不是"纯风格债"**：任何**求值注解**的工具都会炸——`typing.get_type_hints()`、pydantic 模型、dataclass 字段解析，以及 **FastAPI 的路由签名解析**（本项目 `myquant/api/` 正是 FastAPI）。
- 另有少量不同性质者需单独看：`core/transports/__init__.py:32,36` 的 `RedisTransport` / `RabbitMQTransport`。

> **结论**：F821 可以留在基线里，但**必须单独定性后再重基**，不能和 `F541` 这类纯格式项一锅端。
> 这是整个 P0 里**唯一可能牵出真实缺陷**的类别。

**`# noqa` 格式缺陷（v1.1 修正为 4 处失效 / 观测到 6 处异常写法）**：

失效写法是**全角括号紧贴代码**：`# noqa: BLE001（说明）`。ruff 会把 `（` 当作代码的一部分而解析失败：

| 位置 | 写法 |
|---|---|
| `myquant/core/health_check.py:540` | `# noqa: BLE001（NTP 响应解析异常也按不可评估降级）` |
| `myquant/core/health_check.py:768` | `# noqa: BLE001（建连/握手/证书解析失败统一记录）` |
| `myquant/monitoring/meta_monitor.py:182` | `# noqa: BLE001（网络失败记 warning，不阻断主流程）` |
| `myquant/database/migrations/versions/0008_add_value_encrypted.py:48` | `# noqa: BLE001（旧版 SQLite 不支持 DROP COLUMN）` |

**正确写法**（项目内 330 处已在用）：`# noqa: BLE001 - 说明` 或 `# noqa: BLE001 说明`（用半角空格/连字符分隔）。
另有 2 处 `scripts/` 内的 E402 指令格式异常（`清理历史回测输出.py:45`、`垃圾数据清理.py:50`），
因 `scripts/` 属薄入口敏感区，修 noqa 格式时**只改注释、不动代码结构**。

> 这 6 处是**独立缺陷**：有人写了 noqa 以为已抑制，实际长期未生效，而无人发现。
> 修复成本极低（改标点），收益是让"我以为抑制了"变成"确实抑制了"。
