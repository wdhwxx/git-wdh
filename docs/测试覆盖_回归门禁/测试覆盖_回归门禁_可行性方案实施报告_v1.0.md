## 0. 执行摘要

### 0.1 一句话结论

> 本项目**已经具备建成执行级覆盖率门禁的全部技术条件**（套件 4171 用例、门禁核心集 135s、pytest-cov 可用、分层清晰、棘轮范式已在用），

> 一条已经变红的流水线不构成任何保护。**先复基线，再上覆盖门禁。**

## 1. 背景与目标

### 1.1 为什么现在做

项目已建成相当完整的门禁体系：`tests/unit/test_architecture.py` 单文件 1,125 行、30+ 条规则，锁定架构违规数、真环数、超大文件行数、入口白名单、脚本类定义、事件契约、配置死键、**零覆盖模块引用级快照**；CI 侧还有 `RUFF_BASELINE`、`BLE001_BASELINE` 两道 lint 棘轮。这是一套以「基线锁定 + 只减不增 + 新增即红」为核心的成熟范式。

但这套体系里**唯独没有一条门禁管「测试到底执行了多少代码」**：

- 全库检索 `--cov` / `fail-under` / 覆盖率门禁，仅在两份架构治理文档里留下一句自述：**「CI 无 cov/fail-under」**（`鲲鹏量化交易系统_架构分层治理方案_v5.3.md:183`）。无任何实现。
- `R-20` 锁的是**测试函数的数量**（`count >= 3310`，当前实测 3,750，余量 440）——一个断言为空的测试同样满足它。
- `R-19` 锁的是**引用级零覆盖**（"被 tests import 即视为覆盖"，AST 近似）。项目自己在 docstring 里诚实标注了这是近似口径，真实覆盖须由 pytest-cov 判定。

也就是说：**当前对"代码是否被真正执行过"这件事，项目没有任何可阻断的度量。** 这正是本方案要补的位置。

### 1.2 目标

1. 建立**执行级**（pytest-cov 插桩，非引用级近似）覆盖率度量与阻断门禁。
2. 门禁必须**确定性可复现**——不随机器负载、时钟、网络漂移。
3. 门禁必须**进入 CI 并在 PR 上阻断**，且耗时控制在可接受预算内。
4. 门禁判据与项目既有的「棘轮」范式同构，不引入第二套治理语言。
5. 覆盖数字**可解释、可归因**——能回答"哪个高风险模块缺覆盖"。

### 1.3 明确不做的事

- 不追求一次性把覆盖率拉到某个漂亮数字；只做**棘轮 + 分层下限 + 新增门槛**。
- 不把计时/性能基准纳入阻断门禁（见 §3 G-3）。
- 不以覆盖率替代行为正确性（见 §3 G-5，覆盖率高 ≠ 断言有效）。
- 本报告**只出方案，不改动任何代码、配置、CI 与测试**。

## 3. 缺口诊断

| # | 缺口 | 实测证据 | 后果 | 等级 |
|---|---|---|---|---|
| **G-1** | 无执行级覆盖率门禁 | 全库仅 2 处提及"CI 无 cov/fail-under"，均为自述；无任何 `--cov`/`fail-under` 实现 | "代码是否真被执行"完全不可阻断；删除测试只受 R-20 计数约束，而计数余量 440 | **P0** |
| **G-2** | 三个测试目录游离于 CI 之外 | `tests/realism_gate`(15) + `tests/benchmarks`(20) + `tests/scripts`(8) = **43 条**；`ci.yml` 中 `realism` 零命中 | 最新收口的真实性门禁（#376）**零回归保护**；PIT 导出脚本测试从未运行 | **P0** |
| **G-3** | 计时基准不可作为阻断判据 | 本次实跑 `test_engine_throughput_multi_symbol` **失败**：均值 10024.9ms vs 阈值 10000ms（超 **0.25%**）；`INDICATOR_THRESHOLD_MS=200`、`EXECUTION_LATENCY_MS=5` 同为墙钟阈值 | 若纳入门禁，红灯随机器负载随机出现 → 团队必然学会忽略红灯 → **门禁信誉崩塌** | **P0** |
| **G-4** | 测试层 fail-open | 全库 **15 处**运行时 `pytest.skip(`；`test_database.py` 独占 9 处，其中 6 处形如 `try: ... except Exception: pytest.skip("…接口签名不匹配")` | **`except Exception` 把任何真实回归（含签名漂移）静默转为"跳过"**；门禁看到绿，缺陷已进主干。与项目在 `realism_gate` 里反复强调的 fail-closed 原则**自相矛盾** | **P1** |
| **G-5** | 源码断言型测试制造"虚假覆盖" | **36/250** 测试文件使用 `read_text()` 对源码做字符串断言；审计显示 **4 个模块仅由此类测试守护**（`acceptance/chaos_drill.py`、`acceptance/disaster_drill.py`、`core/logger.py`、`core/measurability.py`） | 覆盖率数字上升但**行为未被锁定**——源码重构即假红，源码同形改语义即漏检 | **P1** |
| **G-6** | 标记契约失效 | `pyproject.toml` 声明 `benchmark`/`slow` 两个标记并注明"默认跳过"，但全库**零处**使用；`testpaths` 却包含 `tests/benchmarks` | **裸 `pytest` 必然执行 680s 计时基准**（本次实测已证）；本地开发体验与 CI 行为不一致 | **P1** |
| **G-7** | **lint 棘轮已被突破** | 用 **CI 固定的 ruff 0.16.3**、扫 **git 跟踪文件**（567 个 `.py`，等同干净检出）：**922 项 > 560**；`BLE001` **476 > 382** | 流水线当前即为红；文档设计的"留 45 余量"假设已被 **-362** 现实取代。**已红的流水线无法为任何新门禁提供保护** | **P0** |
| **G-8** | 环境与版本漂移 | 本地 Python **3.11.16** vs CI **3.12**；本地 ruff **0.16.7** vs CI 固定 **0.16.3**；`pyproject` 允许 `ruff>=0.15.0,<0.17.0` | 门禁基线在本地与 CI 之间**不可比**；"本地绿、CI 红"类问题难以定位 | **P1** |

## 5. 总体设计

### 5.1 门禁分层模型（按**风险**分层，不按架构层）

架构层（L0–L6）回答"依赖方向"，不回答"出错的代价"。门禁按资金安全代价分层：

| 层级 | 范围 | 覆盖下限（建议） | 阻断 |
|---|---|---|---|
| **T0 阻断级** | `leakage_gate/`、`realism_gate/`、`risk/`、`execution/`、`live/`、`engine/`、`backtest/{engine,mixed_engine,vectorized_engine}.py`、`strategies/kunpeng_strategy.py` | 总量 ≥ **68%** | ✅ 硬阻断 |
| **T1 严格级** | `core/`、`data_access/`、`database/`、`monitoring/`、`models/`、`indicators/`、`allocation/`、`ml/`、`strategies/`、`backtest/`（其余） | 总量 ≥ **60%** | ✅ 硬阻断 |
| **T2 常规级** | `api/`、`web/`、`gui/`、`utils/`、`acceptance/` | 总量 ≥ **52%** | ✅ 硬阻断 |
| **T3 报告级** | `database/migrations/`、`*_selftest.py`、性能基准 | 仅报告 | ❌ 不阻断 |

> 阈值取"实测值 − 3~4pp"作为余量：T0 71.2%→68%、T1 62.7%→60%、T2 55.3%→52%。
> 余量用于吸收**合理的**测试重构（如合并/重命名测试），同时"只增不减"由总棘轮兜底。

### 5.3 基线棘轮机制

沿用项目既有做法，基线以常量形式冻结在门禁模块内，**修改基线必须与提升覆盖的改动同 commit**：

```python
COVERAGE_BASELINE: float = 62.9          # 门禁核心集口径，2026-10-14 实测 62.99%
TIER_FLOOR = {"T0": 68.0, "T1": 60.0, "T2": 52.0}
FILE_FLOOR = { ... }                     # 只增不减
NEW_FILE_FLOOR = {"T0": 60.0, "T1": 60.0, "T2": 30.0}
```

**只减不增的另一面是"只增不降"**：覆盖上升时须同步抬基线，否则棘轮会松动（`RUFF_BASELINE` 的教训正是长期不校准导致破线 362 而无人察觉——见 G-7）。

### 5.4 覆盖率口径契约（必须先定死，否则数字会被反复误用）

| 契约项 | 规定 |
|---|---|
| 采集口径 | `pytest-cov`，`--cov=myquant` |
| **覆盖集** | `tests/unit` + `tests/leakage_gate` + `tests/realism_gate` + `tests/scripts`；**排除 `tests/benchmarks`** |
| 阻断主口径 | **行覆盖**（`num_statements` / `missing_lines`） |
| 分支覆盖 | **仅报告**，不入阻断（作质量趋势） |
| 与 R-19 的关系 | **不混用**。R-19 为引用级近似（继续保留为廉价快照）；本门禁为执行级。两者数字**禁止相互引用** |
| 与 R-20 的关系 | R-20 测试计数**保留**为廉价兜底，但**明确降级为辅助**；覆盖门禁为其上位判据 |
| 解释权 | 覆盖率数字必须标注口径（是否含基准、行/分支），禁止裸报"63%" |

### 5.5 门禁落位（与既有门禁同构）

推荐落位为**独立测试模块 + 薄入口脚本**，复用项目既有分层纪律：

```
tests/unit/test_coverage_gate.py          # 门禁本体（读 coverage.json，判定 C-1~C-4）
scripts/覆盖率门禁.py                       # 薄入口（脚本纪律：只做参数解析 + 调业务模块）
myquant/leakage_gate/coverage_gate.py     # 业务逻辑：分层表、阈值表、判据实现、报告渲染
```

**为什么归入 `myquant/leakage_gate/`**：该包已登记为 L0，且 `config_deadkey.py` 已是"配置/静态判据 + 报告"的先例（`scripts/配置死键扫描.py` 是其薄入口）。覆盖率判据与它同族——都是"对代码库自身的治理判据"。**若倾向独立成包，须新增 `myquant/quality_gate/` 并同步登记 `MODULE_LAYER`（R-25 要求），否则门禁本体自身会被架构门禁判红。**

> 以下为**建议方案**，本次未执行任何一项。人日按 1 名熟悉本项目的工程师估算。

### 6.0 四条原则

1. **先止血，后加锁**——已红的流水线不构成保护。
2. **棘轮优先于绝对阈值**——只要求"不倒退"，不要求"达标"。
3. **口径先定死，再报数字**——避免 R-19/R-20 混用的历史问题重演。
4. **每一步都可独立回滚**——门禁新增不修改业务代码。

| `test_database.py::TestCleanDataQueries::test_insert_clean_run_from_pipeline_result` | 接口签名不匹配 | ⚠️ **掩盖性**——`except Exception` 吞掉真实契约漂移 |

**最高风险模式**（`tests/unit/test_database.py:595-617`）：

```python
try:
    run_id = cdq.insert_clean_run_from_pipeline_result(data_type=..., symbol=..., ...)
    assert run_id is not None
except Exception:
    pytest.skip("insert_clean_run_from_pipeline_result 接口签名不匹配")
```

`except Exception` 使**任何**真实回归（签名变更、SQL 错误、约束冲突）都表现为"跳过"。这与项目在 `realism_gate` 中坚持的 fail-closed 原则直接冲突，是覆盖门禁上线前应优先处理的一项。
