# 代码变更治理规则

> 本文档是鲲鹏量化交易系统的**代码变更治理宪章**，所有开发者和 AI 助手在修改系统代码前必须逐条阅读并遵守。
>
> 版本：v1.0（2026-09-13）
> 维护位置：`docs/代码变更治理规则.md`
> 蓝图文档：`docs/project_layout_gear2.md`

---

## 一、核心原则：蓝图即宪法

### 1.1 蓝图优先原则

**任何代码变更必须以 `docs/project_layout_gear2.md`（蓝图文档）为唯一权威参考。**

- 新增文件前，必须先查阅蓝图文档中的**目录树**，确认目标文件应放置的目录位置。
- 如果蓝图目录树中**没有对应位置**，说明该文件不应该被创建——要么复用已有模块，要么先更新蓝图再创建文件。
- 蓝图文档中的目录树是**当前系统实际文件结构的精确反映**，不是"理想目标"，二者必须保持 100% 一致。
- 每项任务完成后做Git 提交。

### 1.2 禁止违规添加文件

**严禁在蓝图目录树标注的目录范围之外创建任何 .py / .md / .bat / .yml 等文件。**

违规情形包括但不局限于：
- 在根目录随意创建 `xxx_tool.py`、`temp_script.py` 等"临时脚本"
- 在 `myquant/` 下新建蓝图未标注的子目录（如 `myquant/dashboard/`）
- 在 `scripts/` 下创建蓝图未标注的脚本文件
- 在 `tests/` 下创建蓝图未标注的测试文件

**正确做法：**
1. 查阅蓝图文档 `scripts/` 目录树 → 找到对应位置 → 在该位置创建文件
2. 查阅蓝图文档 `myquant/` 目录树 → 找到对应模块目录 → 在该目录下创建文件
3. 如果确实需要新增目录或文件位置 → **先更新蓝图文档**（追加回写记录 + 更新目录树）→ 再创建文件

### 1.3 脚本薄入口纪律

**`scripts/` 目录下的所有脚本必须是"薄入口"，禁止在脚本内编写业务逻辑。**

| 层级 | 职责 | 示例 |
|------|------|------|
| `scripts/` 脚本 | 参数解析(argparse) + 路径探测 + 调用 myquant 模块 | 只做"胶水"工作 |
| `myquant/` 模块 | 全部业务逻辑、算法、数据处理、文件操作 | 业务核心 |

违规示例（禁止）：
```python
# scripts/xxx.py — 错误！业务逻辑写在了脚本里
import json
def process_data():  # 这是业务逻辑，不应在 scripts/ 中
    ...
```

正确示例：
```python
# scripts/xxx.py — 正确！只做入口
from myquant.xxx.service import main_service
from myquant.utils.file_utils import find_project_root

def main():
    # 参数解析
    # 路径探测
    # 调用业务模块
    main_service()

if __name__ == "__main__":
    main()
```

### 1.4 业务逻辑归 myquant 纪律

**所有业务逻辑代码必须放在 `myquant/` 包内对应的模块目录中。**

- 回测引擎逻辑 → `myquant/backtest/`
- 数据访问逻辑 → `myquant/data_access/`
- 指标计算逻辑 → `myquant/indicators/`
- 通用工具 → `myquant/utils/`
- GUI 逻辑 → `myquant/gui/`

**禁止在 `myquant/` 包外（如根目录、`lib/`、`core/` 等非蓝图标注目录）创建业务逻辑模块。**

## 二、变更流程

### 2.1 变更前检查清单

在动手写代码之前，必须逐项确认：

- [ ] 我已阅读并理解本文档（代码变更治理规则）
- [ ] 我已查阅蓝图文档 `docs/project_layout_gear2.md` 的目录树
- [ ] 我确认新增文件的位置在蓝图目录树中有对应位置
- [ ] 我确认脚本文件遵守"薄入口"纪律（业务逻辑在 myquant/ 内）
- [ ] 我确认没有破坏现有模块的导入关系
- [ ] 我确认新增代码有对应的单元测试（如适用）

### 2.2 变更时操作顺序

1. **查阅蓝图** → 确认文件位置和模块归属
2. **编写代码** → 在蓝图标注的正确位置创建/修改文件
3. **更新蓝图** → 在蓝图文档末尾追加回写记录，更新目录树
4. **运行测试** → 确保 `pytest` 全量通过
5. **提交代码** → commit message 中引用蓝图文档回写记录编号

### 2.3 变更后验证

每次变更后必须执行：

```bash
# 1. 语法检查
python -m py_compile myquant/xxx/new_module.py
python -m py_compile scripts/新脚本.py

# 2. 全量测试
pytest tests/ -v

# 3. 蓝图一致性检查
# 手动对比蓝图目录树与实际文件系统，确认无偏差
```

## 三、蓝图维护规范

### 3.1 回写记录格式

每次代码变更后，必须在蓝图文档末尾追加回写记录，格式如下：

```
N. ✨【回写记录·YYYY-MM-DD·变更标题】变更描述（事实来源：本次落地，代码级核验：...）：
   a. 变更详情1
   b. 变更详情2
   ...
```

### 3.2 目录树同步

追加回写记录的同时，必须同步更新蓝图文档中的**目录树部分**，确保目录树与实际文件系统 100% 一致。

### 3.3 废弃文件标注

被替换/删除的文件不应直接从蓝图文档中消失（会丢失历史上下文），而应：
- 在蓝图文档目录树中保留文件名，但添加注释标注 `# 已废弃，见回写记录·YYYY-MM-DD`
- 或在回写记录中明确说明"XX文件已废弃，由YY文件取代"

## 四、违规处理

### 4.1 发现违规文件

如果在代码审查或蓝图健康检查中发现违规文件：

1. **立即标记**：在文件顶部添加注释 `# ⚠️ 违规文件：不在蓝图目录树中，需迁移或删除`
2. **评估迁移**：判断该文件是否应纳入蓝图（如果是有效功能，更新蓝图后迁移到正确位置）
3. **评估删除**：判断该文件是否已废弃（如果是，安全删除并记录）
4. **更新蓝图**：无论迁移还是删除，都必须更新蓝图文档

### 4.2 定期蓝图健康检查

建议每完成一个里程碑（如 V1 发布、V2 发布）时执行：

```bash
# 检查蓝图目录树中的文件是否实际存在
# 检查实际文件系统中的文件是否都在蓝图目录树中

# 手动检查清单：
# 1. 蓝图目录树中列出的文件是否都存在？
# 2. 实际文件系统中是否有蓝图未列出的 .py/.md 文件？
# 3. 是否有文件放错了目录？
# 4. 是否有已废弃文件未标注？
```

## 五、AI 助手使用须知

> 本文档同样约束使用 AI 助手（如本系统的 Agent）进行的代码生成操作。

AI 助手在执行代码生成任务时必须：

1. **先读蓝图**：加载并阅读 `docs/project_layout_gear2.md`，理解当前目录结构
2. **定位文件**：根据用户需求，在蓝图目录树中找到正确的文件位置
3. **生成代码**：在正确位置生成/修改代码
4. **更新蓝图**：追加回写记录，更新目录树
5. **验证一致性**：确保产出文件与蓝图目录树一致

**禁止行为：**
- 不看蓝图就随意创建文件
- 在蓝图目录树外创建文件
- 生成代码后不更新蓝图
- 创建"临时文件"、"测试文件"、"脚本"而不纳入蓝图管理
