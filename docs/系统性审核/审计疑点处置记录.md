## 疑点 3：Docker live `--broker qmt/ptrade` 平台不匹配

- **判定**：qmt（迅投QMT）/ ptrade（恒生Ptrade）客户端仅支持 Windows，Docker live 容器为 Linux；原实现允许传 `--broker qmt/ptrade` 但无平台校验，误配时需到运行时调用核心动作才因 SDK 占位明确报错，排障体验差且存在"半初始化"模糊状态。

## 疑点 5：Redis `allkeys-lru` 误淘汰业务键

- **状态：已确认并修复（方案 A：volatile-lru，2026-09-11）。**
- **判定**：`--maxmemory-policy allkeys-lru` 允许内存压力下淘汰**任何键**（无论有无 TTL）。当前业务键仅 `RedisCache`（短 TTL 计算缓存，可重建，误淘汰只损性能）与 `redis_bus`（pub/sub 频道，不走键存储，不受 LRU 影响）；但未来若将**不可重建数据**（订单记录、去重窗口、限流计数）放入 Redis，会被静默淘汰造成隐蔽正确性 bug。

### 核查依据

- `docker/docker-compose.yml` redis 段（修复前）：`redis-server --appendonly yes --maxmemory 256mb --maxmemory-policy allkeys-lru --requirepass ...`。
- `myquant/core/cache.py:182` `RedisCache`：计算缓存，短 TTL。
- `myquant/core/transports/redis_bus.py`：pub/sub 频道（非键存储）。
- 限流键（`api/middleware/rate_limit.py`）、事件去重键（`core/event_bus.py`）均为内存实现，不落 Redis。

### 修复内容（方案 A）

- `docker/docker-compose.yml` redis 段：`--maxmemory-policy allkeys-lru` → `volatile-lru`，并加注释说明（只淘汰带 TTL 的缓存键；未设 TTL 的持久键永不静默淘汰）。

### 验证结果

- `docker compose -f docker/docker-compose.yml --profile redis config`：渲染 exit 0，command 含 `volatile-lru`、无 `allkeys-lru`。
- 组合渲染 `--profile web --profile redis`：volatile-lru=1 / allkeys-lru=0 / published 8501=1（auth 网关唯一性保持）——疑点 4 改动无回归。
- 说明：redis 服务带 `profiles: [redis]`（仅按需启动），web profile 不渲染 redis 属预期设计（app 用 sqlite 不依赖 db/redis，Redis 为可选缓存）。
- 备份：`backups/docker-compose_doubt5.bak_20260911.yml`。

## 疑点 6：C3 DLQ 无消费端 / 无告警

- **状态：已评估，决定"什么都不做"，docs 备注留待实盘专项（2026-09-11）。**
- **判定**：C3 轮已保证"消息不丢"——超重试消息进入 DLQ 持久化留存（非丢弃）；DLQ 仅声明绑定、无消费端、无消息量监控/告警，死信消息无限堆积且无人知晓。评估后认为当前阶段（回测/paper 模拟为主、未真钱实盘、死信低频）风险中低、可接受，选择不投入代码改动，风险与处理方案登记于此。

### 核查依据

- `myquant/core/transports/rabbitmq_bus.py:162-187`：DLX 声明 + 主队列绑定 DLX + DLQ 声明绑定（`{queue}.dlq`）；超重试消息 `basic_nack(requeue=False)` 进入 DLQ——**有留存、无消费、无告警**。
- `myquant/monitoring/alerting.py`：`AlertManager` 通过事件总线订阅告警事件（`subscribe_to_event_bus`）——现成告警通道，方案 B 可复用，当前未接线。

### 风险说明（当前可接受的原因）

1. 消息不丢：死信已持久化在 DLQ，非静默丢弃。
2. 安全网：RabbitMQ 内置磁盘水位保护——磁盘接近阈值时**阻塞生产者**而非静默丢消息，最坏情况是 MQ 停摆（服务不可用，会被立即发现），优于静默丢失。
3. 当前业务：死信低频（订单/信号事件），模拟盘失败无真钱损失；排障缺口仅靠人工巡检 RabbitMQ 管理台。

### 实盘专项 TODO（后续按此执行）

- **P1：方案 B（DLQ 消息量监控 + 告警）**——`rabbitmq_bus.py` 增加轻量监控循环（如 60s），passive declare 查询各 DLQ `message_count`，>0 或超阈值 → 日志 + 经事件总线发布告警事件（AlertManager 已订阅）；消息原样保留在 DLQ 供人工恢复。
- **P2：方案 A（DLQ 消费端 + 告警 + 落盘）**——死信量上升、需自动归档/重放时升级：消费 DLQ 消息 → 记录日志 + 告警事件 → **ack 前先落盘/落库留痕**，防止堆积；注意与"人工恢复"意图的关系，需配套重放工具。
- 触发条件：接入真钱实盘、或观察到 DLQ 消息量显著增长。

## 疑点 7：`datetime.utcnow()` 弃用

- **状态：已确认并修复（2026-09-11）。**
- **判定**：`datetime.utcnow()` 自 Python 3.12 起弃用（DeprecationWarning），未来版本移除后调用点直接 `AttributeError` 崩溃；全项目 4 处使用点均为时间戳字符串格式化（无时区算术），替换为 `datetime.now(timezone.utc)` 后 `.strftime()` 输出**完全等价**（格式串无 `%z`，naive/aware 的 UTC 字符串一致），纯机械替换、零行为变化。

### 核查依据

- 运行环境 Python 3.12.13（conda quant）。
- 使用点（4 处）：
  - `myquant/database/queries.py:597`（`%Y-%m-%d %H:%M:%S` 时间戳）、`:602`（`%Y%m%d_%H%M%S_%f` 记录 ID）
  - `myquant/data_access/manager.py:1166`（索引 updated_at）、`:1190`（时间戳）
- 导入方式均为 `from datetime import datetime`（manager.py 另含 timedelta）。

### 修复内容

- 两文件 import 补 `timezone`；4 处 `datetime.utcnow()` → `datetime.now(timezone.utc)`。

### 验证结果

- 全量 `tests/unit` **1253 passed / 2 skipped**。
- `-W error::DeprecationWarning` 严格模式全量 **1253 passed / 2 skipped**——弃用警告清零（此前为全量 20 warnings 之一）。
- 全项目 `utcnow|utcfromtimestamp` 残留 **0**。
- ruff：当前文件与备份文件违规完全一致（E402/I001/F841 均为既有违规，无新增）。
- 备份：`backups/queries_doubt7.bak_20260911.py` / `backups/manager_doubt7.bak_20260911.py`。
