### 1.1 结论

### 1.2 五条核心判断

**① 最关键的一条：系统唯一的"防未来函数最终防线"在失败时不阻断，违规回测仍被标记为成功。**

`myquant/core/lookahead_guard.py` 的契约是"违规即抛 `LookaheadError` 终止"，但三个回测引擎都在 `try/except Exception` 里把它吞成一行 error 日志（`engine.py:538`、`mixed_engine.py`、`vectorized_engine.py` 同构），且 `mark_complete()` 在校验**之前**执行 → `is_success` 恒为 `True`；而失败标记 `extra["lookahead_guard_passed"]` **没有任何生产读取方**（全项目仅测试读它）。结果是：**批量回测 / GUI / 编程调用路径上，含未来函数违规的回测会正常出报告、进指纹缓存、进候选池。**

这一条危害面最大——它使其余所有防未来机制（RSRS 的 `shift(1)`、`LightLookaheadGuard`、截断重算断言）无法收敛为可阻断的结论。叠加第 ② 条（RSRS 选池确实存在未来函数）可推断：**违规是真实存在的，而防线没有把它报出来。**

**② 有三个"纸面上已修好、代码里没修好"的 P0，都在关键路径上。**

- **财务数据下载链路整体失效**（P0-02）：一行 `return []` 违反契约，短路掉全部三条降级源。这解释了为什么"财务数据入库""B 类派生量补数"反复被标记完成、而库里派生量仍为 NULL。
- **RSRS 核心策略的选股池构建使用回测末日数据**（P0-05）：三因子池未按 bar 时点截断，不仅穿越未来，还导致每次调仓输入完全相同 → 池恒定、"20 日调仓"退化为日志空转。**docs 中 +87.38% 之类的绩效数字建立在此之上，不可采信。**

### P0-01｜防未来函数校验失败被引擎吞掉，违规回测仍被标记为"成功"

**根因标签**：`LOOKAHEAD_BYPASS`（**本次审核最严重发现**）

整个系统里唯一被设计为"最终防线"的机制，在生产路径上是失效的。

**证据链（四层，已逐行核验）**：

**第 1 层 — 契约要求失败即终止。** `myquant/core/lookahead_guard.py:445-454,462-474`：

```python
"""回测结束时统一校验（必须调用，规则4要求）
Raises
------
LookaheadError : 存在未来函数违规时抛出
"""
...
if violations:
    ...
    raise LookaheadError(rule_name="防未来函数统一校验", details=summary, ...)
```

模块头部（`:9`）亦声明"回测结束必须调用 `assert_pass()`，不通过则报错终止"。

**第 2 层 — 三个引擎都把异常吞掉。** `myquant/backtest/engine.py:518-544`（`mixed_engine.py:1001-1009`、`vectorized_engine.py:701-709` 同构）：

```python
def _run_lookahead_assert(self) -> None:
    """...校验失败时记录错误日志，但不中断回测结果（回测已完成，结果仍有效）。"""
    ...
    try:
        ...
        self._lookahead_guard.assert_pass()          # :536 违规时抛 LookaheadError
        logger.info("✅ 防未来函数校验通过：未发现未来函数违规")
    except Exception as e:                            # :538 ← 把 LookaheadError 吞掉
        logger.error(f"❌ 防未来函数校验未通过：{e}")   # ← 只记日志
        if self.result is not None and hasattr(self.result, 'extra'):
            self.result.extra['lookahead_guard_violations'] = ...
            self.result.extra['lookahead_guard_passed'] = False
        # ← 函数正常返回；调用方无法得知校验失败
```

**函数签名为 `-> None`，无返回值、不重新抛出** —— 校验失败与通过对上层**不可区分**。

**第 3 层 — 结果状态在校验之前就写死为"完成"。** `engine.py:588-591`：

```python
self.result.mark_complete()          # :588 ← 先把状态置为 completed
# #S3修复：回测结束时运行防未来函数统一校验
self._run_lookahead_assert()         # :591 ← 之后才校验，失败也不改状态
```

`mark_complete()` 使 `models/backtest.py:461` 的 `is_success` 恒为 `True`。

**第 4 层 — 失败标记没有生产读取方。** 全项目 grep `lookahead_guard_passed`：

| 位置 | 用途 |
|---|---|
| `engine.py:544`、`mixed_engine.py:1009`、`vectorized_engine.py:709` | **写入**（仅失败时写） |
| `tests/unit/test_lookahead_wiring.py:54,89,90,110` | **仅测试读取** |

`run_批量回测.py` 与 `myquant/backtest/batch_backtest.py` 对 lookahead **零处理**；`report.py` 也不读该字段。

**综合结论**：

> 在**批量回测 / GUI 批量回测 / 任何编程方式调用三引擎**的路径上，一个含未来函数违规的回测会：正常跑完 → `is_success=True` → 出报告与 CSV → 进指纹缓存与候选池；唯一提示是一行 error 日志（GUI 场景下用户看不到）。两个入口脚本（`run_回测入口.py:357`、`scripts/生成回测报告.py:233`）依赖的也是 `is_success`，而该值在校验前已被置 True，故同样不可靠。

**这直接动摇了"严格无未来函数"这一核心卖点的可信度**：系统确实实现了多层机制（RSRS 闭式 OLS + `shift(1)`、`LightLookaheadGuard`、截断重算一致性断言），但它们的**汇总结论被吞掉了**。叠加 P0-05（RSRS 选池确实存在未来函数）可推断：**违规真实存在，而防线没有把它报出来。**

**修复动作**（建议三件一起做）：
1. `_run_lookahead_assert()` 在校验失败时 `raise`，或返回 `bool` 并让 `on_stop()` 据此 `mark_failed()`；
2. `mark_complete()` 移到校验**之后**，或增加 `mark_failed(reason)` 并使 `is_success` 取两者之与；
3. `batch_backtest.py` / `run_批量回测.py` / `report.py` 读取 `extra["lookahead_guard_passed"]`，为 `False` 时把该标的标为失败、不计入候选池与指纹。

**复验方式**：构造必然违规的回测（如指标里 `shift(-1)`）并**走批量回测路径**，断言该标的不是 completed 且不入候选池。当前预期：completed 且入池。

### P0-10｜vectorized 引擎"幽灵持仓"：持仓不按实际成交量回写

**根因标签**：`ACCOUNTING_DEFECT`（**污染参数扫描与生产阶段一筛选**）

**证据** — `myquant/backtest/vectorized_engine.py:499-542`（已逐行核验）：

```python
# T+1 持仓与成交：position[t] = target[t-1]

exec_shares = np.diff(np.concatenate([[0.0], position]))

...
fill_result = self.matcher.match_vectorized(...)            # :506 真实撮合
fill_qty = fill_result.fill_quantities                     # :519
traded = fill_qty > 0                                      # :520
fill_price_safe = np.where(traded, fill_price, 0.0)         # :522
notional = np.where(traded, fill_qty * fill_price_safe, 0.0)   # :525 费用只算已成交
...
cashflow = np.zeros(n, dtype=np.float64)
cashflow[traded] = sign[traded] * notional[traded] - fees.total_cost[traded]   # :537 现金只按已成交
cash = sub_initial + np.cumsum(cashflow)
position_value = position * closes                         # :541 ← 持仓用的是未修正的 target！
total_asset = cash + position_value
```

**缺陷**：`position` 全程由 `target_arr` 递推，**完全未按 `fill_qty`（实际成交量）回写**；而现金流/费用**只对 `traded` 生效**。

**后果**：在订单**未成交**的日子——停牌（`volume<=0`，撮合把 `fill_price` 置 NaN）或涨停开盘买单被拦截（`matcher` 的 `_check_limit`）——`cashflow=0`（未支出）但 `position` 仍被记为已持有 → **幽灵持仓、净值虚高**。而 `enable_price_limit` 默认为 True 且 `pre_close` 由前收近似，触发相当频繁。

**为什么这是 P0**：`vectorized` 正是**参数扫描**（`kunpeng_param_scanner.py:135 mode="vectorized"`）与**生产阶段一全池筛选**（`run_鲲鹏批量回测.py` `DEFAULT_MODE="vectorized"` → 按成交笔数取 top N → mixed 精算）所用引擎。因此**标的入池与参数排序被系统性污染**，进而影响最终候选池。

**修复动作**：用实际成交量递推持仓，例如
```python
signed_fill = np.where(exec_shares > 0, fill_qty, -fill_qty)
position = np.cumsum(signed_fill)        # 或未成交时把 target 回退为上一持仓
```

**复验方式**：构造一段含 1 根停牌日（`volume=0`）的数据，在停牌日之前发出买入目标，断言停牌日的 `position` **等于前一日的持仓**（而非目标持仓），且 `total_asset` 不出现跳升。


**修复动作**：(a) `return result if result is not None else None`（不要 `or []`），并区分"查询成功且为空"与"查询失败"；(b) 改用关键字传参并自行按代码过滤；(c) 补发前增加"当日无同名 `order_remark` 委托"的二次确认；(d) 为 `_qmt_query_orders` 补单测。

`scripts/实时行情驱动.py:226-227`：`metrics = MetricsCollector()` 后直接 `subscribe_to_event_bus(bus)`，**未调 `register_builtin_metrics()`** → `_ensure_metric`（`metrics_collector.py:431-433`）按 **GAUGE** 自动注册 → `risk_pause_total`/`data_quality_pipeline_runs` 等 COUNTER 被导出为 `# TYPE ... gauge` → 仪表盘 `rate()`/`increase()` 语义错误。应改用 `get_metrics_collector()` 单例。

### P2-14｜"全市场"被等同于"processed 目录现存文件"

### P2-15｜策略参数配置双轨/死配置

`config/strategy_params.example.yaml`：`ma_cross` 用 `short_period/long_period`，而类签名为 `fast_period/slow_period`（`ma_strategy.py:591-596`）→ 静默落 `**params` 失效（默认恰为 5/20 掩盖问题）；`rsi/macd/bollinger` 三块**无对应注册策略**（注册名仅 7 个）→ `create_strategy("rsi")` 抛 `ValueError`。另 `ma_strategy.py:88,143` 的 `pool_top_ratio` 默认 **0.5**，而 `docs/strategy_specs.md:65-67` 写"各因子取前 1/3"、配置 `factor_quantile: 0.33` 标注【预留·未消费】→ **核心策略实际选池口径与规格不一致且不读配置**（双轨）。

### P2-16｜`state_store` 原子写缺 fsync
